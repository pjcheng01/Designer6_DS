## 0. 給接手者的三分鐘版本

- 這是把一套跑了二十多年的 AutoCAD LISP 機械設計外掛（藝祥「機械設計家」Designer6 + POWERPARTS），
  移植到 **DraftSight** 的專案。程式碼是 AutoLISP + DCL，資料是 INI/DAT/DWG/SLD。
- 兩個資料夾、兩套程式：`C:\DESIGNER6_DS`（主系統）與 `C:\POWPARTS_DS`（零件庫）。
  對照組原版留在 `C:\DESIGNER6` 與 `C:\POWPARTS`，**不要動它們**——那是唯一的比對基準。
  唯一的例外是 `SHEET/A1~A4.dwg` 與 `A1~A4tzt.dwg`，這 8 個檔已在 DraftSight 重存過，
  不再與原版一致（§7.1）。
- 移植的主體工作（去加密狗、去 PDM、編碼轉換、載入鏈、選單）**已經做完**，
  現在是逐一功能實測與修 bug 的階段。
- 這個專案**沒有自動化測試**。所有驗證都得由使用者在 DraftSight 裡實際跑指令。
- 最容易踩的三個雷：**檔案編碼**、**換行符與 git**、**DraftSight 與 AutoCAD 的 LISP 行為差異**。
  三者都在下面有專章。

日常工作規範另見 repo 根目錄的 `CLAUDE.md`（Claude Code 會自動載入）。

## 2. 環境與啟動

### 2.0 從零安裝（2026-09-15 整理）

| # | 做什麼 | 產出／效果 |
|---|--------|-----------|
| 1 | 檔案就位：`C:\DESIGNER6_DS`、`C:\POWPARTS_DS` | |
| 2 | DraftSight → Tools → Load Application → 選 `C:\DESIGNER6_DS\setup.lsp` | `config.doc`、`STARTUP.LSP` |
| 3 | 選項 → 支援檔搜尋路徑，加入 `C:\DESIGNER6_DS` 與 `C:\POWPARTS_DS` | 之後 `startup.lsp`／`command.lsp`／DCL 才找得到 |
| 4 | 執行 `CUSTOMIZE` → 載入 `Powsoft_Light.xml` | 選單與工具列（§2.1） |
| 5 | 重開 DraftSight | |

第 2 步 load 下去就會**直接開始問安裝路徑**——`setup.lsp:404` 是 top-level
的 `(c:config_path)`，不是等你打指令。

**第 2 步不需要先設搜尋路徑。** `setup.lsp` 全程用你在提示裡輸入的
`disk_path` 組絕對路徑，完全不依賴 DraftSight 的搜尋路徑：

| 動作 | 程式 |
|------|------|
| 找 setup.lsp | `(findfile (strcat disk_path "\\setup.lsp"))` |
| 載 pub-lisp | `(load (strcat disk_path "\\pub-lisp"))` |
| 開對話框 | `(actdcl (strcat disk_path "\\setup") "setup")` |
| 寫 config.doc | `get_support_path` → fallback 回 `disk_path\` |
| 寫 STARTUP.LSP | `(strcat disk_path "\\STARTUP.LSP")` |

#### `setup.lsp` 只做兩件事

寫 `config.doc`，寫（或補寫）`STARTUP.LSP`。全檔只有兩個 `setvar`，
都是 `cmdecho`——**它從頭到尾沒有碰過搜尋路徑**。

> 原本還有第三件事：`load_softmenu` 會在安裝結束時印一行「選單載入功能
> 待移植至 DraftSight，暫時略過」。那是空殼，而且訊息會誤導——選單早就
> 自動載入了（§2.1）。函式與呼叫已於 2026-09-15（`42820c5`）移除。

所以第 3、4 步必須手動，而且放在 setup 之後也可以。

#### ⚠ 輸入安裝路徑的兩個規矩

1. **結尾不要加反斜線。** `des50_path`／`database_path`／`block_path`
   沒有經過 `canceltxt`（只有 POWERISO／POWERPARTS／MANAGER 三個有，
   `setup.lsp:286-288`），加了會寫出 `DESIGN_PATH=C:\DESIGNER6_DS\\`。
2. **路徑不能有空白。** `c:config_path`（:394）的 `(getstring …)` 沒帶 `T`，
   遇到空白就截斷。

#### ⚠ 不要跑 `C:\POWPARTS_DS\SETUP.LSP`

POWPARTS_DS 有自己一整套 `SETUP.LSP`／`setup.dcl`／`CONFIG.LSP`／`config.doc`，
**完全沒有移植**：

- `SETUP.LSP:130` 用 `(command "menuload" …)`——DraftSight 沒有這個指令
- `CONFIG.LSP` 用 `(getvar "acadprefix")`，還留著 AutoCAD LT 的
  `dctcust`／`fontmap` 分支，且 `(strcat support_path "\\")` 沒有 nil 防護
- `config.doc` 還指向 **`C:\POWPARTS\`**（AutoCAD 原版目錄），而且是中文 key

**正確的路線**：在 DESIGNER6_DS 的 setup 對話框勾 POWERPARTS，它會把
`POWERPARTS_PATH=C:\POWPARTS_DS\` 寫進 **DESIGNER6_DS 的** `config.doc`，
再由 `config.lsp:148-157` 讀出來並 `(load "FUNCTION")`（抓
`C:\POWPARTS_DS\FUNCTION.LSP`）。POWPARTS 不需要自己的安裝步驟。

那套目前不會被誤觸，靠兩層隔離：

1. `POWPARTS_DS\CONFIG.LSP` 只被 `PARTCOM.LSP` 載入，而 `PARTCOM.LSP`
   只被 `POWPARTS_DS\acaddoc.lsp` 載入——**DraftSight 不讀 `acaddoc.lsp`**（§2.2）
2. 就算有人 `(load "config")`，搜尋路徑順序裡 `C:\DESIGNER6_DS\` 排在
   `C:\POWPARTS_DS\` 前面，載到的是移植版

#### 系統變數：`SRCHPATH` 不存在，但改回 `acadprefix` 也沒有用

`config.lsp:44` 與 `setup.lsp:13` 都寫 `(getvar "SRCHPATH")`，兩支檔頭的註解
還說是刻意「改用 SRCHPATH」。**DraftSight 的 325 個系統變數裡沒有 SRCHPATH**
（查 `DraftSight.chm` 裡的 `sv_*.htm`），原版 AutoCAD 用的是
`(getvar "acadprefix")`（`C:\DESIGNER6\setup.lsp:5`）——移植時換成了一個
不存在的變數。

2026-09-15 使用者在 DraftSight 2025（26.4.5056）實測：

```
(getvar "SRCHPATH")    →  nil
(getvar "ACADPREFIX")  →  "C:\Users\…\26.4.5056\Support\;C:\Program Files\Dassault Systemes\DraftSight\Default Files\Support\;C:\DESIGNER6_DS\;C:\POWPARTS_DS\;C:\Users\…\26.4.5056\"
```

兩個結論：

1. **`SRCHPATH` 回 `nil`，不報錯**——`get_support_path` 安靜地掉到 fallback，
   回 `disk_path\`。現況安全。
2. **`ACADPREFIX` 在 DraftSight 是支援的**（說明檔 `sv_acadprefix.htm`，
   本地化名稱 `GetPthDS`，Read/Write），而且路徑是**展開過的**。

**但改回 `acadprefix` 一樣拿不到東西。** `sub_get_support_path` 比對的是
「這一段是不是以 `SUPPORT;` 結尾」，而 DraftSight 每一段的結尾是
**`Support\;`——多一個反斜線**：

```
取最後 8 個字元 → "upport\;"   ≠   "SUPPORT;"
```

所以每一段都不會 match，`support_path` 維持 nil，最後仍然回 `disk_path\`。
兩個變數的結果完全相同。

> 而且 fallback 到 `disk_path` 對「從資料夾直接跑 `setup.lsp`」這個流程
> 反而是**唯一正確**的答案：那個時間點搜尋路徑還沒設，就算 `acadprefix`
> 讀得到也指不到 `C:\DESIGNER6_DS`。

**結論：不需要改程式。** 唯一該修的是那兩支檔頭「改用 SRCHPATH」的註解
——它讀起來像設計決策，其實是選錯變數，只是恰好不影響結果。

⚠ 若日後真的把它改成 `acadprefix`，`sub_get_support_path` 的
`(substr typ (- str_len 7))` 就活了：路徑段少於 8 個字元時起始位置 ≤ 0，
`substr` 會報錯。目前走不到。

#### 診斷：整套功能無聲消失時先看這裡

DraftSight 內建的 `start.lsp`（在它自己的 Support 資料夾）用
`(findfile "startup.lsp")` 找我們這支，載入旗標是 **0＝靜默、失敗也不中斷**：

```lisp
("startup.lsp" . 0)   ;; Former startup.lsp replaced by start.lsp in 2015
```

所以 `startup.lsp` 找不到時**不會有任何錯誤訊息**，只會整套功能無聲消失。
第一個要查的就是搜尋路徑（第 3 步）有沒有掉。

### 2.1 DraftSight 設定

- **Support Files Search Path** 需包含 `C:\DESIGNER6_DS` 與 `C:\POWPARTS_DS`（從零安裝的完整步驟見 §2.0）

- **自動載入**：DraftSight 啟動時執行內建 `start.lsp`，帶起 `startup.lsp`

#### 選單是怎麼自動載入的（2026-09-14 更正）

本節原本寫「目前仍需手動載入，自動化列在待辦」——**那是過時的**。
選單早就自動載入了，靠的是 DraftSight 使用者設定檔裡的一行參照：

```
%APPDATA%\DraftSight\26.4.5056\UI\chinese\traditional\application.xml
```

```xml

重寫（§2.1.1），正是它有被載入的證據**。

> 路徑的斜線是混用的（`C:/DESIGNER6_DS\Powsoft_Light.xml`，前面正斜線、
> 後面反斜線）。那是 DraftSight 自己寫出來的原樣，照抄就好，不要「順手修正」。

**不建議用腳本去改 `application.xml`**：檔案 961 KB、由 DraftSight 擁有，

1. **參照是分語言的。** 只有 `chinese\traditional` 那份有。若把 DraftSight
   的介面語言換成英文或簡體，讀的是另一個目錄的 `application.xml`，
   那裡沒有這行 → **選單整個消失**，而且不會有任何錯誤訊息。
   換語言後要重跑一次 `CUSTOMIZE`。
2. **參照是分版本的。** 路徑裡的 `26.4.5056` 是 DraftSight 版本號。
   升級後會是新的目錄；檔頭提到的「移轉功能」理論上會帶過去，
   但**未查核**。升級後若選單不見，先檢查新版本目錄裡有沒有這一行。

### 2.1.1 ⚠ 手改 `Powsoft_Light.xml` 的兩個陷阱

`Powsoft_Light.xml` 是 DraftSight 的**部分自訂檔**，由
`%APPDATA%\DraftSight\<版本>\UI\chinese\traditional\application.xml`
以這一行參照：

```xml
<partial_file file_name="C:/DESIGNER6_DS\Powsoft_Light.xml"/>
```

**陷阱一：DraftSight 擁有這個檔，會在啟動時覆寫它。**

2026-09-11 實測的時間軸：

| 時間 | 事件 |
|------|------|
| 14:05 | 手動編輯檔案並 commit，新增兩個選單項 |
| 14:07 | DraftSight 啟動 → **檔案被重寫，那兩項消失** |
| 14:14 | DraftSight 關閉後重新編輯 → **檔案未再被動過** |

結論：**結束時不寫回，只在啟動時寫。**
所以外部修改要生效，必須在 DraftSight **完全關閉**時進行，
改完直接啟動即可；不需要跑 `CUSTOMIZE` 重新載入。

**陷阱二：一個 `definition` 只能屬於一個容器。**

這個檔案是「`definition` 定義指令 + `menu` / `toolbar` 以
`definition_ref` 參照」的兩段式結構。直覺上同一個指令應該共用一份
`definition`，避免改了一處漏另一處——**但 DraftSight 不接受**。

驗證方式是統計整個檔案：

```
menu 參照的 definition    : 271 個
toolbar 參照的 definition : 276 個
兩者重疊                  : 0 個   ← 決定性證據
```

共用會讓 DraftSight 在載入時把該節點判定為無效並**靜默丟棄**
（連帶前後的分隔線），檔案裡看不出任何錯誤訊息。
要在選單和工具列都放同一個指令，就得寫**兩份 `definition`**、各自一個 GUID。

**選單用的 `definition` 慣例**（統計 271 筆得出）：

| 欄位 | 慣例 |
|------|------|
| `command` | 不加 `^P`（258/271） |
| 各 `*IconName` | 全部留空（271/271） |
| `description` | 填入與 `name` 相同的文字（271/271） |

工具列用的則相反：有圖示、`description` 留空。

**改完必做的四項檢查**：

```python
ET.fromstring(s)                      # XML 合法
len(refs - ids)                       # 孤兒 definition_ref 必須是 0
len(menu_refs & toolbar_refs)         # 共用的 definition 必須是 0
len([u for u in set(uids) if uids.count(u) > 1])   # 重複 UID 必須是 0
```

另注意本檔是 **UTF-8 / 純 LF**（DraftSight 自己寫出來就是 LF）。
`git checkout` 會因 `core.autocrlf=true` 把它轉成 CRLF，
所以用腳本改寫時要先正規化成 LF，寫回時也用 LF。

### 2.1.2 盤點「選單／工具列 ↔ 程式」對應（2026-09-14）

移除功能之後，選單和工具列上常會留下按不動的項目。做法是把 XML 裡每個
`definition` 的指令對回實際存在的函式：

1. 掃兩個 repo 全部 `.lsp` 的 `(defun c:xxx …)`（當時 163 支、924 個函式）
2. 讀 DraftSight 的內建指令表
   `Default Files\Alias\alias.xml`（1,362 個）
3. 剝掉 `^C^C` / `^P` / `'` 前綴與參數，逐一比對

⚠ **三個容易犯的判定錯誤**（都實際踩過）：

- **指令以 `&` 開頭就是 Designer 自己的指令，不可以把 `&` 剝掉去比對 DraftSight
  內建。** `&co` 與內建的 `co`（COPY）是兩回事，剝掉會產生假陰性。
- **`-toolbar xxx s` 是 DraftSight 內建指令**（顯示某工具列），不是孤兒。
  但要另外檢查它指向的**工具列名稱**是否還存在。
- **`definition_ref` 有兩種用途**：指向 `definition` 的 GUID，以及
  `type="2"` 的「工具列內嵌工具列」用符號名（如 `POWSOFT.AUXDRAW1`）。
  檢查孤兒參照時要排除後者，否則會誤報。
  ⚠ **但排除不等於沒問題**——見下面第 4、5 點。

- ⚠ **`type="2"` 的符號引用在 DraftSight 根本解析不到。** 第一輪盤點
  看到那 20 筆對不到 `definition`，查出都是 `type="2"` 就放過了，
  **沒有再驗證那些符號名稱是否真的指向什麼**。實際上
  `POWSOFT.AUXDRAW1` 這類名稱在整個檔案裡各只出現一次（就是引用本身），
  所以兩個容器工具列打開後是空的。要驗就數一次出現次數。

- ⚠ **`.lsp` 裡「有 `(defun c:xxx`」不等於那個函式真的存在。**
  它可能包在一個永遠不成立的條件式裡。`config.lsp:142-145` 的四個
  `c:iso*` 就是這樣：

  ```lisp
  (setq poweriso_path (… (getfile_val config.doc "POWERISO_PATH") …))
  (if (and poweriso_path (/= "" poweriso_path))
    (progn (defun c:isomenu1 …) (defun c:isomenu2 …)
           (defun c:isoblk1 …)  (defun c:isoblk2 …)))
  ```

  而 `config.doc` 那一行是 `;;POWERISO_PATH=`（**被註解掉**）。
  `getfile_val` 做的是 `=` 前面的**完全比對**，找 `POWERISO_PATH` 對不上
  `;;POWERISO_PATH`，回 nil → 四個函式從來沒被定義過。

  **掃描時要一併檢查兩件事**：哪些 `defun` 的括號深度 > 0（在條件式裡），
  以及它的守衛 key 在 `config.doc` 裡是不是被註解掉了。

## 3. 編碼規範（最重要的一章）

### 3.1 規則

| 類型 | 必須編碼 | 理由 |
|------|---------|------|
| `.lsp` | **UTF-8**（無 BOM） | DraftSight 2025 可正確讀取 |
| `.dcl` | **cp950 / Big5** | DraftSight 不支援 UTF-8 DCL，`load_dialog` 回傳 -1 |
| `.ini` `.doc` `.dat` `.txt` | **cp950 / Big5** | DraftSight 的 `open`/`read-line` 以 cp950 讀檔，UTF-8 會亂碼 |
| `.md` `.gitignore` `CLAUDE.md` | UTF-8 | 給人和工具讀 |
| `.ps1` | **UTF-8 with BOM** | ⚠ 唯一需要 BOM 的類型。Windows PowerShell 5.1 沒看到 BOM 就用系統 ANSI（cp950）讀 `.ps1`，中文註解與字串會變亂碼並直接造成語法錯誤。2026-09-15 加 `tools\build_release.ps1` 時踩到 |

**同一個檔案內絕不可混用編碼。**

> **`.txt` 資料檔那一列已於 2026-09-10 實機證實**，此前只在 `.dcl` / `.ini` 上驗證過。
> 做法是準備兩份內容相同、編碼不同的檔案，在命令視窗各讀一次比對：
>
> ```lisp
> (defun rdtest (fn) (princ (strcat "\n===== " fn " =====")) (setq f (open fn "r")) (while (setq l (read-line f)) (princ (strcat "\n" l))) (close f) (princ))
> (rdtest "C:\\DESIGNER6_DS\\test_utf8.txt")
> (rdtest "C:\\DESIGNER6_DS\\test_cp950.txt")
> ```
>
> 結果：UTF-8 版的「人字紋踏板」顯示為「鑿箏綵」之類的亂碼，cp950 版完全正常。
> **要驗證某個編碼能不能用，一定要實際讀一次，不要從別的檔案類型推論。**

#### `COMMAND.lsp` 的還原方法（唯一真正需要還原的一支）

損傷機制是確定性的：那次轉換把 Big5 的位元組**當成 UTF-8** 解碼。所以受損行裡
不只有 U+FFFD——湊得出合法 UTF-8 序列的位元組對會變成希臘字母那類碼位，
Big5 第二位元組落在 ASCII 範圍的會漏成 `w` 這種混進程式碼的雜訊字元：

```
原檔    ;;使用者自定圖庫
受損後  ;; U+FFFD U+03E5 U+03AA U+0326 U+06E9 'w' U+FFFD U+03EE 'w'
```

既然機制確定，就可以反過來當驗證器：

```python
def damage(o):
    return o.encode('cp950').decode('utf-8', errors='replace')
```

在原版檔案裡找 `damage(o)` 與受損行**完全相等**的那一行——相等就是逐字元的證明，
不是啟發式配對，而且移植期間被改過的行不可能誤配（改過就不會相等）。
`COMMAND.lsp` 463 個受損行全部還原，找不到對應 0 行、候選歧義 0 行。

還原後跑過的 6 項驗證：

1. **反向驗證**：每個變動行重新 `damage()` 一次，必須逐字元等於舊版
2. 行數、換行（這支是**純 LF**，見 §4）、有無 BOM 均不變
3. 頂層 `defun` 數量與**名稱**完全相同（489 個）
4. 所有 `(load "…")` 完全相同
5. 括號平衡不變
6. 字串字面值數量不變，且已無任何一個含 U+FFFD

> **規則不變：不要再對 `.lsp` 跑批次編碼轉換**，尤其不要對不確定是不是文字檔的
> 東西跑。上面那招不是轉換，是「拿原檔的正確內容替換，並用確定性的損傷函式
> 證明配對正確」。逐檔做、每一行都要有證明，配不上就不動。

### 3.4 動手前的檢查指令

```bash
# 驗 UTF-8
python3 -c "open('SHSCAL.lsp','rb').read().decode('utf-8'); print('UTF-8 OK')"
# 驗 cp950
python3 -c "open('shscal.ini','rb').read().decode('cp950'); print('cp950 OK')"
# 找出檔案裡非 UTF-8 的行號（用來抓混編碼）
python3 - <<'PY'
bad=[]
for i,l in enumerate(open('SHSCAL.lsp','rb').read().split(b'\n'),1):
    try: l.decode('utf-8')
    except UnicodeDecodeError: bad.append(i)
print('非 UTF-8 行:', bad or '無')
PY
```

**改 cp950 檔案時的正確做法**（`.dcl` / `.ini` / `.doc` / `.dat`；`.lsp` 已無 Big5）

一般編輯工具會把檔案寫成 UTF-8，改一個 cp950 檔就會造成**單一檔案內混編碼**——
`CLAUDE.md` 明令禁止，而且此專案已犯過一次（c690ade 修的 `SHSCAL.lsp`）。
要用 python 讀 cp950 → 修改 → 以 cp950 寫回：

```python
import io
s = io.open(p, 'rb').read().decode('cp950')
s = s.replace(OLD, NEW)          # OLD/NEW 都是 str
io.open(p, 'wb').write(s.encode('cp950'))
```

**改完一定要驗「它不是合法 UTF-8」**——這是確認沒有混進 UTF-8 位元組最快的方法：

```python
d = open(p, 'rb').read()
d.decode('cp950')                # 必須成功
try:
    d.decode('utf-8')
    print('警告：竟然也是合法 UTF-8，可能混入了 UTF-8 位元組')
except UnicodeDecodeError:
    print('非 UTF-8，符合 cp950 檔應有的狀態')
```

（純 ASCII 的檔案兩種都會通過，那沒問題；有中文的 cp950 檔一定不是合法 UTF-8。）

**Big5 檔的括號平衡也要用 cp950 解碼後再掃**——位元組層級掃描對 Big5 不可靠
（§7.2），但先 `decode('cp950')` 再掃字元就正確了。

## 4. 換行符與 git

repo 歷史是以 `core.autocrlf=true` 從 Windows 提交的：**版本庫存 LF、工作目錄存 CRLF**。

若在沒有這個設定的環境（例如 Linux、或透過網路磁碟掛載）操作 git，
`git status` 會把 **265 個檔案全部誤判為已修改**——那不是真的改動，是換行符解讀差異。

```bash
git config --get core.autocrlf    # 必須是 true
git config core.autocrlf true     # 不是就設定它（已於 2026-08-28 設好）
```

**症狀辨識**：`git status` 一次冒出上百個沒印象改過的檔案 → 先查這一項，不要照單全收去 commit。
一旦把 CRLF 提交進版本庫，之後所有人的 diff 都會爛掉。

### 4.1 ⚠ 孤立的 CR：掃描器會看錯，git 也不會幫你正規化（2026-09-14）

有 3 支 `.lsp` 含**孤立的 CR**（`\r` 後面沒有接 `\n`）：
`AUXEDIT.lsp` 9 個、`LAYER.lsp` 10 個、`MANABALL.lsp` 2 個，共 21 個。

全部是同一個形狀 —— `…<CR>)<CRLF>`，也就是**移除加密狗那一輪的簽名**。
那一輪把

```lisp
(if (and (= jin "#$%")(= #### 85))(setq FFF t))(WHILE (/= FFF nil)(setq ppss sspp)
   …
   (SETQ FFF nil))
```

換成 `(progn …)`，收尾那個括號前面的換行只寫了一半。

**陷阱一：括號檢查器會看錯。**

把整個檔案按 `\r\n` 切行，孤立 CR 會留在行內當成普通字元。
如果它前面剛好是 `;` 註解，後面那個括號就會被**誤判成註解的一部分**：

```
  );if<CR>)          ← 掃描器：那個 ) 在註解裡，不算
                        直譯器：看它把不把單獨 CR 當行尾，可能算
```

`LAYER.lsp` 就是這樣被算出 depth = +1 的。實際影響不是掃描器的問題而已——
若直譯器也不把單獨 CR 當行尾，`(defun c:dlay` 會一路吃到檔尾，
它之後的 30 個函式全部定義不出來（12 個有分派點）。已於 `57e236f` 修掉。

> ⚠ **但書：那 12 支指令是在修完之後才實測的**（2026-09-14 全數通過）。
> 所以證實的是「這個修法可用」，**沒有回答「修之前它們是不是真的壞的」**——
> 也就是 DraftSight 究竟把不把單獨的 CR 當行尾，仍然不知道。
> 要確定的話得拿修改前的版本再跑一次，目前沒有必要。

> 掃描時兩種解讀都算一次：`replace('\r\n','\n')`（悲觀，CR 留在行內）
> 與再 `replace('\r','\n')`（樂觀，CR 也當行尾）。兩者結果不同就是有這個問題。
> 這是繼 §5.20 的 `;| … |;` 之後，括號檢查器第二個已知盲點。

**陷阱二：git 不會對含孤立 CR 的檔案做 CRLF→LF 正規化。**

所以這 3 支在**版本庫裡存的是 CRLF**，跟其他檔案（存 LF）不一樣。
後果是：**只要你把孤立 CR 清光，git 就會把整檔正規化，產生整檔 diff**
（`LAYER.lsp` 實測 1,973 行全變）。

因此 `57e236f` 先只修了那一個有語意影響的（並實測通過），其餘 21 個留到
後來以 `a9ab16c` 獨立一次清掉——**確實觸發了整檔重新正規化**：
三支的 blob 由 CRLF 變 LF，diff 顯示 2,278 行變更，但把換行全部壓成 `\n`
之後與前一版逐位元組相同，證明只有行尾變了。

**現況：全專案 202 個文字類納管檔案，孤立 CR 為 0。**
（`.DWG` / `.SLD` / `.EXE` 等二進位檔內含 `0x0D` 位元組屬正常，不在此列。）

### git 鎖檔陷阱

透過網路磁碟或受限掛載操作 git 時，`.git/index.lock`、`.git/HEAD.lock`、`.git/objects/tmp_obj_*`
可能因為無刪除權限而殘留，卡住後續所有 git 指令（`fatal: Unable to create index.lock: File exists`）。

```bash
rm -f .git/index.lock .git/HEAD.lock .git/objects/maintenance.lock
find .git/objects -name "tmp_obj_*" -delete
```

## 5. DraftSight 與 AutoCAD 的 LISP 行為差異

這是移植過程中最花時間的部分。以下每一條都是實際踩過的坑。

### 5.1 `load_dialog` 需要副檔名

AutoCAD 的 `(load_dialog "shscal")` 會自動補 `.dcl`，DraftSight 不會，會回傳 -1。

**修法**：`PUB-LISP.lsp` 的 `actdcl` 一律補副檔名 → `(load_dialog (strcat filename ".dcl"))`。已修。

### 5.2 ✅ `read-line` 不吐檔尾空行（2026-09-11 證實）

**症狀**：`shscal.ini` 最後一段（`**凱柏圖框`）的最後一筆 `ASMA3` 在圖紙尺寸清單裡消失，
但非最後一段（`**凱柏零件圖框`）的 `A4` 正常。

**成因**：`SHSCAL.lsp` 的 `read_autoshscal_data` 原本把每段讀到的列一路 `cons` 進 `rdlist`，
再用 `(reverse (cdr rdlist))` 取出——那個 `cdr` 是**刻意**用來丟掉「段尾空白行」產生的 nil。
整個解析因此相依於「每段後面都有一行空白行」。檔案最後一段的空白行位在 EOF 前，
AutoCAD 的 `read-line` 會先回 `""` 再回 `nil`，DraftSight 推測是直接回 `nil`，
`rdlist` 的頭就變成最後一筆資料而被 `cdr` 丟掉。

**修法**（commit 52f6a64）：改成只收集以 `(` 開頭的有效資料列，直接用 `(cons nn (reverse rdlist))` 組裝，
不再依賴空白行、也不再用 `cdr` 丟東西。這個修法不管 `read-line` 的實際行為如何都正確。

**實機證實（2026-09-11）**：以 `SETITEM.DOC` 實測。該檔實際有 20 行，
最後一行是空白（檔案以 `…環首桿")\r\n\r\n` 結尾）：

```lisp
(setq f (open (strcat bmanager_path "SETITEM.DOC") "r") n 0 last "")(setq d (read-line f))(while d (setq last d)(setq n (1+ n))(setq d (read-line f)))(close f)(princ (strcat "\n共讀到 " (itoa n) " 行，最後一個非 nil 的是 [" last "]"))
```

結果：

```
共讀到 19 行，最後一個非 nil 的是 [("HRINGS" "ITEM26" "I26" "" 0 "環首桿")]
```

**`read-line` 跳過了檔尾的空白行，直接回傳 `nil`。** AutoCAD 會先回 `""` 再回 `nil`。

**這造成的第二次事故**（commit 7ab7c91）：符號庫全系列（`oilgas1/2`、
`QUICKTAH2`、`HRINGS2`、`userblk2` …）完全無法使用。`USERBLKM.lsp` 的
`Binilist` 靠「讀到不是 `(` 開頭的行」結束迴圈：

```lisp
(while flag
     (setq data (read-line openfile))
     (if (= "(" (substr data 1 1))        ; data 是 nil 就「無效的參數」
      (setq item_list (cons (read data) item_list))
      (setq flag nil)))
```

AutoCAD 讀到 `""` → `(substr "" 1 1)` 得 `""` → 正常結束。
DraftSight 直接得到 `nil` → `(substr nil 1 1)` → **錯誤: 無效的參數**。

**修法**：條件改為 `(and data (= "(" (substr data 1 1)))`。

> **通用教訓**：原始碼裡任何「靠空白行、檔尾格式、行數當 sentinel」的寫法，在移植版都是高風險。
> 看到 `(cdr rdlist)`、`(reverse (cdr ...))` 這類寫法要優先懷疑。
>
> **更具體的排查規則**：所有 `(setq X (read-line f))` 之後對 `X` 做
> `substr` / `strlen` 的地方，都要確認迴圈條件擋得住 `nil`。
> 安全的寫法是 `(while data …)`（條件本身就是那個變數）；
> 危險的是 `(while flag …)` 這種——條件與變數無關，`X` 變 `nil` 也不會停。
> 2026-09-11 掃描全專案：安全 48 處、需逐一檢視 22 處、已確認並修復 1 處。
> **掃描結果是線索不是結論（§9.5）**，其餘 21 處要逐一讀完整個函式再判斷。

### 5.3 `attdia 0` 無效

AutoCAD 的 `attdia 0` 讓 `INSERT` 改在命令列詢問屬性，可以用 `repeat n (command "")` 跳過。
DraftSight 的 `attdia 0` **完全無效**，插入含屬性的 block 時強制彈出對話框。

**影響**：曾擋住 `auto_insert_attsheet` 插入 `*tzt.dwg` 的流程。
**已解決**——改用 `attreq 0` 繞過，見 §5.7。

### 5.4 `entnext` / `entget` 限制

在某些情況（特別是 `command` 執行後），`entlast` 取得的 entity name 可能失效。
必須在 `command` **執行完成後立即**取得，不能跨函式傳遞。

### 5.5 動態作用域行為不同

`input_attedata` 從 `ATOshscal` 呼叫時，讀不到 `ATOshscal` 的區域變數（`?scl`、`sfilename` 等）。

**修法**：呼叫前把需要的值存成全域（命名慣例 `&&vctr`、`&&scl`、`&&sfilename`…），
並把 `attdata_list` 從 `ATOshscal` 的區域變數列表移除讓它變全域。已修。

### 5.6 ⚠ `unload_dialog` 的位置：批次補這種東西最容易出事

**症狀**：使用者按下對話框的「OK」之後，DraftSight **隨機閃退**，跟跑第幾次無關。

**成因**（2026-09-10 查出，commit e35afc7 修復）：`MANAPART.lsp` 的
`automakepart_ok` 裡有一行沒被註解的 `(unload_dialog dcl_id)`。
那個函式是 `action_tile "accept"` 的回呼，執行時**對話框還開著**：

```lisp
(defun automakepart_ok()          ; action_tile "accept" 的回呼
   ...
   (unload_dialog dcl_id)         ; ① 對話框還開著就卸載它的 DCL
   (setq automakepart_fg t)
   (done_dialog)                  ; ② 關閉一個定義已被卸載的對話框
)
;; 回到 c:automakepart
(start_dialog)
(unload_dialog dcl_id)            ; ③ 對同一個 dcl_id 再卸載一次
```

use-after-free 加 double-free。**當不當掉取決於當下的記憶體狀態，所以是隨機的。**

**它怎麼跑進去的**：批次補 `unload_dialog` 時（commit 4cd4282「所有 LSP 補
unload_dialog」）插錯位置——被放進一段**已整段註解掉的巢狀對話框程式碼**中間，
自己卻沒加註解符號。原版 `C:\DESIGNER6\MANAPART.lsp` 這個位置沒有這一行。

**正確的規則**

- `unload_dialog` 只能在 `start_dialog` **返回之後**呼叫
- **絕不可**出現在 `action_tile` 的回呼函式裡
- 同一個 `dcl_id` 只卸載一次

**偵測方法**（值得在每次批次改動後重跑）

```
可疑樣式 A：同一個 defun 內，unload_dialog 出現在 done_dialog 之前，
            且它前面沒有 start_dialog  →  對話框還開著就卸載
可疑樣式 B：同一個 start_dialog 之後連續出現兩個以上 unload_dialog
            （中間只隔空白或註解）      →  double-free
```

樣式 A 全專案只有這一處，已修。**樣式 B 還有 48 處、跨 20 個檔案**，見 §7.4。

> **通用教訓**：對這種老程式做**批次插入**特別危險——它們充滿了整段註解掉的舊碼，
> 腳本看不出「這一行在註解區塊裡」。批次改完一定要用**語意層級**的檢查重掃一次，
> 不能只看「有沒有補上」。這個 bug 從 4cd4282 潛伏到現在才被使用者用閃退踩出來。

### 5.9 ⚠ 全形空白 U+3000 會被讀成符號（2026-09-10 證實）

**DraftSight 的 LISP 讀取器不把全形空白當空白。** 它會被讀成一個名稱是全形空白的
**未繫結符號**，於是整個運算式多出一個引數、而那個引數是 `nil`。

```lisp
(if (= "partref"　(cdr (assoc 2 (entget ename))))(progn ... ))
;;            ↑ U+3000，位元組 E3 8080
```

實際被讀成 `(= "partref" nil (cdr ...))`——三個引數的比較，**永遠不成立**。
整段靜默跳過，**沒有任何錯誤訊息**。

**這不是推論。** 全自動指標球的球號寫不進「組合件號」就是這個造成的（commit 00f5971）。
當時有兩個候選原因（全形空白、大小寫），實測 `(cdr (assoc 2 (entget e)))` 回傳
**小寫 `partref`**，證明 `(= "partref" "partref")` 本來就成立、大小寫不是原因；
移除全形空白後功能立刻正常。全形空白是唯一變因。

**為什麼特別難抓**：它在編輯器裡看起來就是一個空白，`grep` 也不會特別標出來，
而且**原版 AutoCAD 檔案裡就有**（AutoCAD 的讀取器顯然容忍它），所以 diff 原版也看不出來。

**偵測方法**（找程式碼區、非字串非註解的 U+3000）

```python
FW = chr(0x3000)
# 逐行判斷每個字元是否落在字串內或註解後，只回報落在程式碼區的
```

全專案掃描結果 5 處，已修 1 處（`MANAPART.lsp`）。剩餘 4 處：

| 位置 | 內容 | 可達性 |
|------|------|--------|
| `CREATBLK.lsp:38,57` | `(command "block"　bname …)` | `c:&creatblk` 在 `COMMAND.lsp:815`，**不在選單上** |
| `XBLOCK.lsp:38,57` | 同上 | **沒有任何地方載入，死碼** |

但因為兩者都不在選單上，優先度低。

### 5.10 block 名稱保留插入時的大小寫（2026-09-10 證實）

程式用 `(command "insert" (strcat powdesign_dwg_path "partref") …)` 插入，
DraftSight 就把 block 名稱存成**小寫 `partref`**（圖檔本身是 `PARTREF.dwg`）。

實測方法：

```lisp
(setq e (car (entsel "\n請點選一個資訊點: ")))(princ (strcat "\nblock 名稱 = [" (cdr (assoc 2 (entget e))) "]"))
```

由此推出兩條規則：

| 寫法 | 是否受影響 |
|------|-----------|
| `ssget` 過濾器 `(cons 2 "PARTREF")` | **不受影響**，CAD 內部比對不分大小寫。程式裡大量使用，全都安全 |
| LISP 自己用 `=` 比對 `(= data2 "PARTREF")` | **區分大小寫**，拿小寫的實際值比大寫字面值不成立 |

> ### ⚠ 但「找到大小寫不符」不等於「應該修」
>
> 這一條比上面兩條更重要。2026-09-10 掃出 4 處用 `=` 搭配大寫 `"PARTREF"` 的地方，
> 逐一讀完之後，**沒有一處應該改**：
>

> | `MANAPART.lsp:1171` `c:ball` | 確實沒 `strcase`，但不在選單也不在 `COMMAND.lsp`，開發殘留 |
> | `MANAPART.lsp:1231` `c:test` | `c:ball` 的複製品，開發殘留 |
> | `MANAPART.lsp:2812` `c:edit_bomp` | **絕對不能改** |
> | `MANAPART.lsp:3573` `get_sheetatt` | **誤報**——3571 行已經先 `strcase` 過了 |
>
> `c:edit_bomp` 那一處值得細看。它是 `cond` 的其中一個分支，而該分支把 `ee` 設成 `t`：
>
> ```lisp

>       (get_bomdata&show_data (car ent))
>       (setq ee t))                        ; ← ee 設成布林真值

>

### 5.11 ⚠ `write-line` 拿到 `nil` 檔案代碼會靜默中止（2026-09-10 證實）

**這是這個專案「無聲失敗」最大的單一來源。**

`(open path "w")` 失敗時回傳 `nil`。把 `nil` 當檔案代碼傳給 `write-line`，
DraftSight **不報錯，但會中止整個運算式的求值**——同一行後面的東西都不執行，
函式就這樣安靜地結束。**AutoCAD 在這裡是會丟出錯誤訊息的。**

實測（在命令視窗逐行貼，看 `princ` 有沒有印出來）：

```lisp
(setq qq (open "c:\\bompath.txt" "w"))(princ (strcat "\n① qq=" (if qq "有效" "nil")))
(write-line "test" qq)(princ "\n② write-line 沒有中斷")
```

結果：① 印出 `qq=nil`，**② 完全沒有輸出**——`princ` 沒被執行，也沒有任何錯誤訊息。

**造成的實際問題**：「物料清單匯出到Excel」(`&bomtree1`) 完全沒反應。
`bomtree` 第 3 行就是 `(open "c:\\bompath.txt" "w")`，而 **Windows 10 的 UAC 下
非提權執行寫不進 C 槽根目錄**，於是整個功能在第 3 行無聲死亡（commit 見 §6）。

**排查方法**：症狀是「跑了指令但完全沒反應、沒有任何訊息」時，
先找該函式裡所有的 `(open ... "w")`，特別是寫到**固定絕對路徑**的：

```
c:\bompath.txt  ← MANAPART.lsp 有 4 處：
                   trans_data_todwg_db(412) / c:opendwg(433)
                   c:insdwg(509) / bomtree(1343，已修)
```

然後在命令視窗逐行重跑函式開頭幾行，看 `princ` 從哪一行開始不印了。

> **仍待處理**：`c:opendwg`、`c:insdwg`、`trans_data_todwg_db` 三處還沒修。
> 它們跟 `bomtree` 不同——那三個**真的會啟動 `manadwg.exe`**（437、512 行），
> 而 `manadwg.exe` 正是靠 `C:\bompath.txt` 認系統路徑的。所以不能只是加守衛跳過，
> 得先查清楚 `manadwg.exe` 那一端是不是把路徑寫死了。

### 5.12 `VSMIN` / `VSMAX` 永遠回傳 `(0 0 0)`（2026-09-10 證實）

DraftSight **不支援** AutoCAD 的 `VSMIN` / `VSMAX`（目前視埠的左下／右上角）。
`getvar` 不是回傳 `nil`，而是回傳 `(0 0 0)`——**這比回傳 nil 更難抓**，
因為它看起來像個合法的點，不會立刻出錯，而是在後續運算裡才炸。

實測（同一張圖，有圖元）：

```
vsmin    = 0,0                    ← 不支援
vsmax    = 0,0                    ← 不支援
extmin   = 2599.796,-4192.45      ✓ 正常
extmax   = 6952.092,-3258.263     ✓ 正常
viewsize = 2185.233               ✓ 正常
```

**造成的實際問題**：「放圖框定比例」(`&autoSHSCAL`) 在**圖面上有圖元時**
出現「錯誤:除以零」，空圖反而正常。`SHSCAL.lsp` 的 `comp_cur_limits` 原本是：

```lisp
S_RATIO (/ (- (car RIGHT_UP) (car LEFT_DOWN))          ; vsmax.X - vsmin.X = 0
           (- (cadr RIGHT_UP) (cadr LEFT_DOWN)))       ; vsmax.Y - vsmin.Y = 0  ← 除數
```

空圖不出錯的原因很間接：`ATOshscal` 先做 `(command "select" "ALL" "")`，
空圖選不到東西，`comp_cur_limits` 開頭的 `(ssget "p")` 回 `nil`，
**整段被跳過**，`SX` 維持 `nil`，`cala_scale` 走 else 分支填 1:1。
有圖元才會走進來踩到除法。

**修法**（commit 見 §6）：改用 `EXTMIN` / `EXTMAX`——那本來就是圖形範圍，
直接相減即得寬高，語意更直接，而且**整個除法都不需要了**：

```lisp
LEFT_DOWN (getvar "extmin")
RIGHT_UP  (getvar "extmax")
SX (- (car RIGHT_UP)  (car LEFT_DOWN))
SY (- (cadr RIGHT_UP) (cadr LEFT_DOWN))
```

全專案只有這一處用到 `VSMIN`/`VSMAX`（原版也只有這 2 行），沒有其他地方會踩到。

> **通用教訓**：DraftSight 對不支援的系統變數**不一定回傳 `nil`**，也可能回傳
> 一個「型別正確但數值全零」的值。看到 `(getvar "…")` 用在**除數**或**分母**上時，
> 先實測那個變數在 DraftSight 到底回傳什麼，別假設它跟 AutoCAD 一樣。
> 這跟 §5.3（`attdia` 設得進去卻被忽略）是同一類陷阱：**變數存在 ≠ 行為相同**。

### 5.13 `done_dialog` 之後的 `set_tile` / `mode_tile` 無效（2026-09-10 證實）

AutoCAD **容忍**在 `(done_dialog)` 之後繼續呼叫 `set_tile` / `mode_tile` /
`act_pop_list`，**DraftSight 不容忍**——那些呼叫全部落空，且不報錯。

**造成的實際問題**：「定義材料清單欄位」編輯完子視窗關閉後，主對話框的清單
仍顯示舊值，要整個關掉重開才看得到新值。`DFSYSTEM.lsp` 的
`modify_field_defbom_ok` 原本是：

```lisp
(done_dialog)                     ; modify 對話框在這裡就關了
(act_pop_list bomlist "bom")      ; 之後這些 tile 呼叫全部落空
(set_tile "bom" index)
```

**巢狀對話框要更新母對話框，正確的時機只有一個**：母對話框的
`action_tile` 回呼裡、子對話框 `start_dialog` **返回之後**。

```lisp
(defun 子對話框 (…)
   (actdcl … )
   (action_tile "accept" "(子對話框_ok)")   ; ok 裡只設旗標 + done_dialog
   (start_dialog)
   (unload_dialog dcl_id)
   (if 旗標                                  ; ← 更新母對話框放這裡
      (progn (act_pop_list … ) (set_tile … )))
)
```

**不能只是把 `done_dialog` 移到最後**。子對話框往往有**與母對話框同名的 tile**
（本例的 `bom` / `pdm` / `wid` 在子對話框是編輯框、在母對話框是清單），
子對話框還開著時 `set_tile` 會打到子對話框自己的 tile，一樣不對，
而且 `act_pop_list` 對編輯框操作還可能出錯。

**順帶注意**：搬到正確位置後，必須用旗標區分「按確定」與「按取消」。
原本的程式碼沒有這個區分——因為那串呼叫反正全部落空，看不出差別。

### 5.14 字串字面值是「位元組原樣傳遞」（2026-09-10 觀察）

［觀察，樣本有限］DraftSight 似乎**不對 `.lsp` 裡的字串字面值做重新編碼**，
而是原樣傳遞位元組。

**證據**：`PDMBOM3.LSP` 是 Big5 檔，第 51 行
`(write-line (strcat "檔號;組立圖料號;" tittxt) ff)` 裡的
`"檔號;組立圖料號;"` 是 Big5 位元組。寫出的 `pdmbom3.txt` 以 cp950 解碼
**中文完全正確**，沒有亂碼。

**推論出來的分工**：

| 用途 | Big5 的 `.lsp` 會不會出問題 |
|------|---------------------------|
| `write-line` 寫進 cp950 資料檔 | **不會**（位元組原樣過去，兩端都是 Big5）|
| `princ` 到命令視窗顯示 | **會**（顯示層期待 UTF-8，見 §3.1）|
| 拿去跟外部字串比對 | **會**（例如 `HP-K.LSP` 把中文紙張名稱餵給 PLOT，§7.3）|

**這修正了 v4 稍早的一個誤判**：手冊原本說「`PDMBOM3.LSP` 把中文寫進匯出檔
表頭，跟 §7.3 是同一類問題」——**不是**。`HP-K.LSP` 的中文要拿去跟印表機
驅動回報的名稱**比對**，那才會壞；單純寫進檔案不會。

> **但 `.lsp` 一律用 UTF-8 的規則不變**（§3.1）。這一條只是說明「Big5 的
> `.lsp` 為什麼有時候看起來沒事」，不是可以放心留著 Big5 的理由——
> 只要那個字串有一天被拿去 `princ` 或比對，就會壞。

### 5.15 DCL 載入偶發失敗，且 DraftSight 的錯誤訊息是壞的

### 5.16 ⚠ 排查任何「沒反應」之前，先 `(setq *error* nil)`

**這條應該排在所有排查步驟的第一位。**

`&autoSHSCAL` 會把 `te_err_pub` 裝成全域 `*error*`（`SHSCAL.lsp:618`），
而且**正常結束時不會還原**——`ATOshscal` 從頭到尾沒有卸下它。
唯一的還原在 `te_err_pub` 自己裡面，又被守衛擋住：

```lisp
(if oerr (setq *error* oerr))     ; oerr 是 nil 時不成立，於是不還原
```

`(setq oerr *error* *error* te_err_pub)` 在原本的 `*error*` 是預設值（nil）時，
`oerr` 就是 nil。**所以只要成功跑過一次「放圖框定比例」，這個 session 之後
所有的錯誤訊息都會被吞掉**，只剩下 `*Cancel*`。

`te_err_pub` 還有兩個問題：

- `(if (/= msg "Function cancelled") (princ …))` — 會吞掉 `(exit)` 產生的訊息
- `(setvar "osmode" &oldos)` — `&oldos` 是 nil 時在**錯誤處理器內部**再炸一次，
  把原本的錯誤訊息徹底沖掉

實測 `&oldos=nil  oerr=nil  *error*=自訂`，三者同時成立。

**排查時第一件事**：

```lisp
(setq *error* nil)
```

2026-09-11 那次排查繞了十幾輪，直到做了這一步才看到真正的
「錯誤: 無效的參數」與「警告:程式被 EXIT 指令終止」。

**已修並於 2026-09-11 在 DraftSight 實測通過（55bc60f + 147d9b8）。**
這個問題有兩層，兩層都修了。

**第一層：處理器裡的有條件還原**（55bc60f）。全專案 9 處寫成
`(if oerr (setq *error* oerr))`，`oerr` 為 nil 時直接跳過還原。
改成無條件 `(setq *error* oerr)`——設成 nil 本來就代表「還原成內建處理器」。
同一批也為處理器內的復原動作補上 nil 守衛（`osmode`、`cecolor`、`celtype`、
`blipmode`、`dimsah`、`dimblk1/2`、`dimfit`、`&oldos`），避免處理器內部自爆。
位置：`AUXDIM.lsp` ×5、`AUXDRAW1.lsp`、`MANAPART.lsp`、`SHSCAL.lsp`、`LAYER.lsp` 各 1。

**第二層：正常結束時不還原**（147d9b8）——這才是真正的汙染源。
處理器裡的還原只有「真的出錯」才會跑到；而 14 個指令**即使全程沒出錯**，
跑完後 `*error*` 仍停在自訂處理器上。已在每個正常結束路徑補上 `(setq *error* oerr)`：

| 檔案 | 指令 |
|------|------|
| `AUXDIM.lsp` | `c:dimgeo`、`c:dimgeo_base`、`draw_dimgeo`、`wedding`、`c:con_dim`、`drawdim_keydim` |
| `AUXDRAW1.lsp` | `c:ho1`、`c:ho2`、`c:ho`、`c:sha` |
| `MANAPART.lsp` | `c:bomlist` |
| `SHSCAL.lsp` | `ATOshscal` |
| `campro.lsp` | `campro_insert_sheet` |
| `LAYER.lsp` | `ssx` |

`LAYER.lsp` 的 `ssx` 不能直接在尾端加 `setq`——它的回傳值被 `LAYER.lsp:103` 的
`(setq gro-ent (ssx))` 取用，直接加會把回傳值換成處理器本身。要先接住再還原：

```lisp
(defun ssx (/ olderr ssx_ret)
  (setq olderr *error* *error* ssx_er)
  (setq fltr (ssx_fe))
  (setq ssx_ret (ssx_gf fltr))
  (setq *error* olderr)
  ssx_ret)
```

**盤點時的陷阱**：安裝點實際是 **17 處**，不是一眼看到的 14 處。
有三個是分兩行寫的，只比對單行的 `(setq oerr *error* *error* X)` 會漏掉：

```lisp
(setq olderr *error*
      *error* at_err)        ; ASCTEXT.lsp:176、AUXDIM.lsp:280、LAYER.lsp:142
```

重掃後 17 個安裝點全部在正常結束時還原，0 處遺漏。

**還有一個未處理的前提**：`oerr` 在這些函式裡**都不是區域變數**（沒列在 `/` 後面），
是全域的。目前這 13 支彼此不互相呼叫（已逐一確認呼叫端都沒有安裝處理器），
所以不會互相覆蓋；但日後若新增巢狀呼叫，內層結束時會把 `*error*` 還原成
外層的處理器而不是內建處理器。要根治就得把 `oerr` 加進各自的區域變數表。

**第三層：頂層 `(defun *error* (msg) (princ))`**（2026-09-14，3ab7f2c）。
前兩層處理的是「存回慣例」；這一層是完全不同的機制，而且影響更廣。

8 支檔案裡共 **19 處**寫成：

```lisp
(defun *error* (msg)
   (princ)
)
```

它**不在任何函式裡**，是頂層運算式——`(load "MANAPART")` 一跑到這一行，
全域 `*error*` 就被永久換成「收到訊息但什麼都不做」，而且沒有任何地方會還原。
`MANAPART.lsp` 與 `DFSYSTEM.lsp` 幾乎每個功能都會載入，所以實務上
**開機用過一兩個指令之後，這個 session 就再也看不到錯誤訊息**。

已全部改為照常顯示，只濾掉使用者主動取消／中斷這三種不算錯誤的訊息：

```lisp
(defun *error* (msg)
   (if (and msg
            (/= msg "Function cancelled")
            (/= msg "quit / exit abort")
            (/= msg "console break"))
      (princ (strcat "
Error: " msg))
   )
   (princ)
)
```

分布：`BLKSUBCR.lsp` 1、`DFSYSTEM.lsp` 7、`HP-K.LSP` 1、`MANAPART.lsp` 1、
`OUTBLK.lsp` 1、`S_ALLBLK.lsp` 1、`S_ASMSET.lsp` 6、`TRANSDWG.lsp` 1。

**掃描這類問題的方法**：不能只 grep `(defun *error*`——巢狀在函式內的那些是正常
慣例，不該動。要**逐字元追括號深度**，只挑深度為 0 的。專案裡的 `toperr.py`
就是這樣做的，並且要先把 `;| … |;` 區塊註解挖空（§5.20），否則深度會算錯。

**改完不要用「還有幾個頂層 `*error*`」當驗收標準**——它們改完仍然是頂層定義，
數字不會變。要驗的是**函式本體會不會顯示訊息**（比對本體裡有沒有
`princ … msg`）。

### 5.17 `princ` 印不出函式內容，無法用來辨別重複定義

AutoCAD 的 `(princ 某函式)` 會印出完整的 lambda，可以看出目前生效的是哪一份。
**DraftSight 只印出不透明參照**：

```
(princ actdcl)  →  <Sub: #000001c5:bd609408 ACTDCL>
```

**可用的替代方法**：重新載入前後**比對位址**。位址改變就代表定義被換掉了。

```
(princ actdcl)        → <Sub: #000001c5:bd609408 ACTDCL>
(load "pub-lisp")
(princ actdcl)        → <Sub: #000001c5:bd609258 ACTDCL>   ← 位址變了
```

### 5.18 檢查清單：DraftSight 的「無聲失敗」

這個專案至今遇到的靜默失敗樣態。**共同點是不報錯**，只能靠逐行 `princ`
或實測 `getvar` 抓出來。指令「跑了但沒反應／沒效果」時，照這張表逐項排除：

| # | 樣態 | 症狀 | 章節 |
|---|------|------|------|
| **0** | **`*error*` 被換掉且未還原** | **所有錯誤訊息都被吞掉，只剩 `*Cancel*`** | **§5.16** |
| 1 | 全形空白 U+3000 被讀成符號 | 判斷永遠不成立，整段跳過 | §5.9 |
| 2 | `write-line` 拿到 `nil` 檔案代碼 | 中止整個運算式，函式安靜結束 | §5.11 |
| 3 | 系統變數回傳「型別正確但全零」 | 後續運算才炸（例如除以零） | §5.12 |
| 4 | `done_dialog` 之後的 tile 呼叫 | 畫面不更新，資料其實已改 | §5.13 |
| 5 | 大小寫敏感的字串比對 | 分支永遠不走（但**未必該修**）| §5.10 |
| 6 | `read-line` 檔尾直接回 `nil` | `(substr nil …)` →「無效的參數」 | §5.2 |
| 7 | `actdcl` 呼叫端多寫了 `.dcl` | 對話框開不起來，訊息說找不到 `xxx.dcl.dcl` | §5.19 |

**第 0 項要先做**——不先還原 `*error*`，下面幾項都看不到錯誤訊息。
原始碼層面的成因已於 2026-09-11 修掉（§5.16，55bc60f + 147d9b8），
但**這一項不能從清單上拿掉**：舊 session 裡殘留的汙染、尚未重新載入的 `.lsp`、
或日後新寫的處理器，都會讓它再次出現。排查時照樣先 `(setq *error* nil)`。

**排查的標準流程**（2026-09-11 整理，那次繞了十幾輪才走完）：

1. **`(setq *error* nil)`** —— 讓錯誤訊息出得來（§5.16）
2. **直接呼叫底層函式**，繞過選單與 `c:` 分派，確認是哪一層的問題
3. **把函式內容逐行貼進命令視窗**，每行後面接 `(princ "\n標記")`，
   看標記印到哪裡停——這是定位斷點最有效的方法，比讀程式碼快得多
4. 拿到**真正的錯誤訊息**之後才動手改

第 3 步在 2026-09-10/11 定位了三個問題（`bomtree` 的 `write-line`、
`get_block_set` 的 `Binilist`、`block_getrealstr` 未定義），每次都是幾分鐘內見效。
相對地，沒有先做第 1 步就靠症狀推論的那幾輪，連續猜錯八次。

### 5.20 括號檢查器不認得 `;| … |;` 區塊註解（2026-09-14）

本專案慣用的括號平衡檢查（剝掉字串與 `;` 行註解後數 `(` `)`）**對 AutoLISP
的區塊註解 `;| … |;` 會誤報**。

`HP-K.LSP` 有一段 `;|(defun c:batch_plot() … )|;`（160-198 行），
檢查器只把 `;|(defun c:batch_plot()` 當行註解剝掉，區塊內其餘的括號照算，
於是永遠回報 `paren = -1`。

**判斷方法**：拿 HEAD 版跑同一個檢查。數字一樣就是本來如此，不是這次改壞的。
要正確計算就得先移除區塊註解：

```python
BLK = re.compile(r';[|].*?[|];', re.S)   # 先剝這個，再剝字串與行註解
```

目前已知只有 `HP-K.LSP` 用到區塊註解。

### 5.21 `FILEDIA` 的語意與 AutoCAD 相反，`CMDDIA` 管的也不是同一件事（2026-09-14）

兩個在 AutoCAD 腳本裡很常用的系統變數，在 DraftSight 換了名字，其中一個還**反過來**。
來源是安裝目錄的 `Help\english\DraftSight.chm`（用 7-Zip 解開）裡的
`cmdvar/sv_filedia.htm` 與 `cmdvar/sv_cmddia.htm`。

**`FILEDIA` → DraftSight 叫 `EnblNavDlgs`，0/1 的意思跟 AutoCAD 相反：**

| 值 | AutoCAD | DraftSight（官方說明原文） |
|----|---------|---------------------------|
| 0 | 走命令列提示 | Uses a dialog box version of the command |
| 1 | 跳檔案對話框 | Uses command window prompts for the command |

DraftSight 的預設是 **1**，也就是**預設就走命令列提示**。
AutoCAD 腳本裡慣用的 `(setvar "filedia" 0)` 搬過來會**打開**對話框，正好相反。

⚠ 這是照官方說明文件的表格抄的（原始 HTML 的 `<td>` 逐格確認過，不是轉換出錯），
**未實機查核**。這個對應關係看起來不太直覺（`EnblNavDlgs` = 0 卻是「用對話框」），
真的要依賴它之前先實測一次。

**`CMDDIA` → DraftSight 叫 `EnblCmdDlgs`，管的範圍完全不同：**

DraftSight 的說明只寫「決定 SmartLeader 與 Leader 指令要用命令列提示還是
就地文字編輯器」，預設 0，而且 1 那個選項標著 not yet supported。
**跟出圖對話框毫無關係。**

**同一類的第三個：`SRCHPATH` 在 DraftSight 根本不存在。**

`config.lsp:44`／`setup.lsp:13` 用它取支援路徑，實測回 `nil`（不報錯）。
DraftSight 對應的是 **`ACADPREFIX`**（`sv_acadprefix.htm`，本地化名稱
`GetPthDS`，Read/Write），原版 AutoCAD 用的也正是它。細節與「為什麼改回去
也沒用」見 §2.0。

所以原本 `HP-K.LSP` 裡的

```lisp
(command "cmddia" 0)          ; AutoCAD：關掉 PLOT 的對話框
```

搬到 DraftSight 是沒有作用的。已在 HP-K 重新移植時拿掉——`-PRINT` 本來就是
命令列版本，不需要靠變數壓對話框。

## 7. 已知問題

### 7.1 ✅ `autoSHSCAL` 屬性寫入（已解決，2026-09-10）

> v3 把這條列為「最高優先、擋住主線」，**但那是誤判**：v3 的程式碼片段是手打進手冊的，
> 沒跟原始檔同步，而修法早在 commit 75f9e4e 就進去了。教訓見文末。

**最終寫法**（[`SHSCAL.lsp`](../SHSCAL.lsp) 的 `auto_insert_attsheet`）

```lisp
(command "insert" sfilename vctr ?scl ?scl "0")                 ; 插入外框（無屬性）
(setvar "attreq" 0)                                             ; ← 關鍵：靜默填入預設值
(command "insert" (strcat sfilename "tzt") vctr ?scl ?scl "0")
(setq tzt_ent (entlast))                                        ; 必須立即取得（§5.4）
(setvar "attreq" 1)
;; ... MOVE 圖框 ...
(if attdata_list (chg_sheetatt tzt_ent attdata_list))           ; 用對話框的值覆寫
```

與原版的差異：

| | 原版（AutoCAD） | 移植版 |
|---|---|---|
| 吃掉屬性提示 | `(repeat attqty (command ""))` 按 27 次 Enter | `attreq 0`，不需要 |
| Y 比例 | `""`（接受預設） | 明確傳 `?scl` |
| 覆寫條件 | `(if (= "1" instype) ...)` | `(if attdata_list ...)` |
| 找不到 tag | 無檢查 → `(entmod nil)` | `(if data1 ... (princ "[WARN] ..."))` |

`attqty` 因此變成**死變數**（還被設定但沒有消費點）。這是好事：
原版依賴「ini 裡手工維護的數字」要跟「DWG 實際屬性數」一致，移植版不再有這個相依性。

**IDX 的根因**（實測通過前的最後一個障礙）

實測時出現 `[WARN] chg_sheetatt: tag not found: IDX`。查核結果：

| 來源 | 數字 |
|------|------|
| `shscal.ini` A1~A4 屬性定義 | 27 |
| `shscal.ini` 宣告的 `attqty` | 27 |
| `A4tzt.dwg` 當時實際 ATTDEF | **26**（缺 IDX）|

`shscal.ini` 一直是對的，**是 DWG 漂移了**——IDX 屬性定義在某次編輯中從圖框檔裡消失。
這一個根源同時造成兩個症狀：`chg_sheetatt` 找不到 tag，以及原版 `(repeat 27 ...)`
會對 26 個提示多按一次 Enter。

`C:\DESIGNER6` 原版的 `shscal.ini`（27 筆、`attqty=27`）與 `A4tzt.dwg`（26 個）**同樣不一致**，
所以這是原版就存在的資料漂移，不是移植造成的。原版沒出事的原因推測是
`(= "1" instype)` 這個較窄的條件讓 `chg_sheetatt` 很少被走到。

**修法**：在 DraftSight 裡為 `SHEET/A1~A4tzt.dwg` 各補一個 `IDX` 屬性定義

### 7.4 ✅ 重複的 `unload_dialog` 已清除（2026-09-14）

#### 怎麼證明刪得安全（值得日後照抄的作法）

`(unload_dialog x)` 本身是**平衡運算式**，刪掉不會改變括號深度。所以括號檢查
過不了關就等於沒驗到——真正要確認的是**兩行在同一個巢狀層級**：
若一行在 `(if …)` 裡、另一行在外，刪錯就會改變語意。

作法是逐處比對「兩行各自開始之前的括號深度」，相等才動，不相等就跳過。
43 對全部相等，0 處需要跳過。

這正是 §5.6「批次補這種東西最容易出事」的反面示範：**先證明再動**，
而且把證明寫成腳本的一部分，不是靠抽樣看幾處。

### 7.6 ⚠ 設定對話框改了，為什麼圖面沒變（2026-09-14）

`&deflayer`（設定圖層系統變數）改完顏色存檔之後，**圖裡已經存在的那個圖層不會變色**。
這常被當成「設定沒生效」，但它其實是兩件事，要分開看：

| 觀察 | 意義 |
|------|------|
| 重開對話框，顏色欄仍是舊值 | **真的沒生效**——`get_layerdef` 沒讀到 `System.ini`（見下） |
| 對話框顯示新值，但圖面圖層沒變色 | **既有設計**，不是壞掉 |

**為什麼圖面不變**：顏色只在「圖層不存在、要新建」時才會被套用。
`PUB-LISP.lsp` 的兩個建層函式都是同一個寫法：

```lisp
;; clauc（:536）與 make_layer（:448）
(if (null (tblsearch "LAYER" lay))          ; 不存在才建立並設顏色
    (command "layer" "n" lay "c" col lay "lt" lty lay ""))
(command "layer" "s" lay "")                ; 已存在就只切換過去
```

而 `deflayer_ok`（`DFSYSTEM.lsp:288`）寫完 `System.ini` 之後**只呼叫
`(get_layerdef)`**，沒有任何「同步更新圖面上既有圖層」的動作。

所以新設定只會影響：

- 還沒有該圖層的圖（下次建層時用新顏色）
- 切換到該圖層時的「目前顏色」（`make_layer` 尾端的 `(command "color" lacolor)`）

要驗證設定有沒有生效，正確做法是**重開對話框看數值**，或開一張還沒有該圖層的新圖。

> 2026-09-14 實測：使用者把文字註解層改成 5 號色存檔，重開對話框顯示 5（✅ 讀取端
> 已修好），圖面上既有的 TEXT 層維持原色（既有設計）。

**若要讓它連既有圖層一起改**，那是行為變更，得在 `deflayer_ok` 尾端補一段
對 `deflayer_list` 逐項下 `(command "layer" "c" 顏色 圖層名 "")`。尚未實作，
因為會動到既有圖面的外觀，需要先確認這是客戶要的。

#### 讀取端曾經整個沒接上

`get_bomdef` / `get_bomlistdef` / `get_layerdef` 原本只回傳程式內建的預設值，
完全沒讀 `System.ini`——但這三個對話框都會寫進 `System.ini`，而且寫完就緊接著
呼叫這三個函式，**原意顯然就是要它們重新讀檔**。已於 `8bc7704` 修好，詳見該 commit。

其中 `BOM_FIELD_DEF` 的內建預設值與 `System.ini` 的實際內容**完全不同**
（5 欄英文 vs 6 欄中文），而且內建版本自己就與 `QTY_POS=5` 矛盾——
第 5 欄是 `Remark` 不是 `Qty`。改讀 ini 之後才一致。

`QTY_POS` 那條路徑在 `getbomtxt_list`（`BOM.lsp:1405`），只有
`&drawbom_list` 與 `&bomlist_txt` 會走到；`&bomlist`（`MANAPART.lsp:3092`）
是**另一套實作**，它自己直接讀 `BOM_FIELD_DEF`，與 `defbomlist_list` 無關。
兩組材料清單功能並存、資料來源不同，排測試時很容易誤判——
2026-09-14 就先拿 `&bomlist` 當驗證對象而白測了一次。
四項（`&deflayer`、`&defball`、`&defbom`、`&bomlist_txt`）於同日全部實測通過。

#### 當時的狀況

#### 差異一：`&chtodim` 兩個版本做的是**完全不同的事**

```lisp

808-816  (load "auxedit")      ; 後一組，勝出

### 9.5 ⚠ 掃描結果是線索，不是結論

這個專案已經因為「照模式批次判斷」踩過三次，每次的代價都不小：

| 時間 | 事件 |
|------|------|
| 早期 | Big5→UTF-8 批次轉換用 `errors='replace'`，11,953 個中文永久損毀（§3.3）|
| 317cccd / 4cd4282 | 批次補 `unload_dialog`，插進註解區塊造成隨機閃退（§5.6），另留下 48 處重複（§7.4）|
| v3 手冊 | 照「檔案清單 + 分類」建立現況，沒跟呼叫關係走，四處失實（§10.9）|
| f55c9c1 | ini key 中文改英文，**只改了讀取端**，7 處寫入端仍用中文 key（§10.3）|

2026-09-10 又差一點踩第四次：掃出 4 處「大小寫敏感的 block 名稱比對」，
看起來全該加 `strcase`，逐一讀完之後**沒有一處應該改**，其中一處改了還會弄壞
正常功能（§5.10）。

**規則**

- 掃描器只做字面比對，**不追資料流、不看可達性、不知道那條路徑本身是不是壞的**
- 每一處命中都要**把整個函式讀完**再判斷，特別要看：
  - 前面幾行是不是已經處理過了（`get_sheetatt` 就是這樣誤報的）
  - 這個分支被跳過時，程式走的是哪條路、那條路是不是反而正確
  - 這支程式在不在 `COMMAND.lsp` 的分派表或選單上（打不到的就別花時間）
- **批次改完要用語意層級的檢查重掃一次**，不能只確認「有沒有改到」
- 有疑慮時，先請使用者測一次「現在到底壞不壞」，比繼續推論便宜太多

### 9.6 ⚠ 改完 `.lsp` 一定要重新載入，否則測的是舊的

`COMMAND.lsp` 的每個指令都是**延遲載入**，而且守衛是「沒載過才載」：

```lisp
(cond ((null c:makepart)(load "manapart"))(t (princ)))
```

只要那支檔案在這個 session 裡已經被載入過，**它就不會重新載入**——您改了磁碟上的
`.lsp`，跑的還是記憶體裡的舊版本。症狀是「明明改對了卻完全沒反應」。

改完之後，測試前先在命令視窗重新載入該檔：

```lisp
(load "manapart")
```

或直接重開 DraftSight。**這一步會省下很多次白測**——2026-09-10 就因為漏了這步，
一度以為 `bomtree` 的修正沒有效果。

   歷史」的前提是 **private repo**（§10.7 的 `c3d131d`）——**交付給別人就
   推翻了那個前提**。
2. **`docs/` 裡也有同一組明文密碼**（`瘦身分析-PDM與外部程式.md` §7），
   所以連「只排除 .git」都不夠。
3. **`.git` 很肥**：100.6 MB 的 `DESIGNER6_DS` 有 48.7 MB 是 `.git`；
   `POWPARTS_DS` 的 73.4 MB 裡有 17.3 MB。

#### ⚠ 最大的雷：不要用 `git archive --format=tar` + Windows 的 `tar.exe`

`tar.exe` 會把 tar 裡的 UTF-8 檔名當 cp950 解，**中文檔名全毀**：

```
功能對照表.md                →  _撠銵_md          ← 連副檔名的點都被吃掉
TUTORIAL\濾清機零件圖\        →  TUTORIAL\瞈暹_璈隞嗅_\
```

這就是 §3 那個編碼老毛病，只是這次發生在**檔名**上，而且不會有任何錯誤
訊息。第一版 release 就是這樣做的，靠事後比對中文檔名才抓到。

#### 正確做法：`git checkout-index`

由 git 自己把納管檔案寫出去，檔名交給 git 處理：

```powershell
git checkout-index -a -f --prefix=C:/DESIGNER6_RELEASE/DESIGNER6_DS/
```

`--prefix` **必須用正斜線且以斜線結尾**。這個做法自動：

- 不含 `.git`
- 不含被 `.gitignore` 擋掉的執行期殘留（`Thumbs.db`、`*.bak`、`campro.txt`、
  `SWAPFILE.TXT`、`system.swr`、`SYSTEM.NEW`… 2026-09-15 當時共 34 個）
- 只含 `HEAD` 的內容——所以**動手前先確認 `git status` 乾淨**，否則交付的
  和你手上跑的不是同一份

#### 要另外排除的（文件與開發用檔）

| repo | 排除 |
|------|------|
| `DESIGNER6_DS` | `docs/`、`tools/`、`功能對照表.md`、`CLAUDE.md`、`.gitignore` |
| `POWPARTS_DS` | `CLAUDE.md`、`.gitignore` |

`docs/` 與 `功能對照表.md` 是給**接手維護的人**看的，不是給使用者的；
而且 `docs/` 含明文密碼。

#### 打包

用 7-Zip 並加 `-mcu=on` 強制 UTF-8 檔名：

```powershell
& 'C:\Program Files\7-Zip\7z.exe' a -tzip -mcu=on -mx=7 out.zip src\
```

#### 交付前的六項驗證（都踩過或差點踩到）

1. 沒有 `.git` 目錄
2. 沒有 `.md` 檔
3. 全文搜不到那組明文密碼字串
4. 沒有執行期殘留（`Thumbs.db`／`*.bak`／`campro.txt`…）
5. **中文檔名逐一比對原始工作區**——這項是抓到 `tar.exe` 問題的唯一手段
6. 匯出檔數 == `git ls-files` 的檔數（扣掉排除清單之後）

| `D` | 日期 | `getsys_date` + `DATE_FORMAT` | 否 |

### 10.5 資訊點資料源（`&automakepart`）

2026-09-10 改造。原本靠 CAMPRO ERP 查詢，資料庫已不存在，改為讀取外部檔案。

**原本的路（已廢止）**

```
autocreat_bomp  →  campro_getbom_data (campro.lsp:342)
   ① 讀 database.txt 第 1 行 → 欄位對應「料號;TAG3;TAG10;…」

   ⑤ (command "delay" 5000)
   ⑥ get_sqlrun_data("CamproBom.txt")             ← 讀回結果
```

**LISP 從來沒有直接連過資料庫**，它只是寫一個請求檔、讀一個結果檔。
所以改造要換掉的只是「誰來產生結果檔」。

這條路其實斷了兩層：資料庫不存在，而且 `camprobom.bat` 的內容是
`c: / cd \ / cd designer6 / camprobom.exe`——**`cd` 到的是原版目錄而非 `_DS`**。
就算資料庫還在，從 `_DS` 執行也會讀錯 `campro.txt`、寫錯 `CamproBom.txt`。

**現在的路**

```
ERP「XML」匯出（UTF-16LE）
        ↓  tools\xml2partdata.py（只在更新清單時跑）
partdata.txt（cp950、分號分隔、CRLF、4.7 MB、83,190 筆）
        ↓  read_partdata_file (MANAPART.lsp)，讀檔時用圖層清單過濾
資訊點屬性
```

執行期**不需要任何外部程式**，也不需要 `delay`。掃描 83,190 筆約 3~5 秒，
比原本固定等 5 秒再加啟動 PowerBuilder 程式還快。

**`partdata.txt` 格式**

```
料號;TAG3;TAG9;TAG10;TAG4;TAG8;TAG5          ← 第一行是欄位對應
00462;人字紋踏板;Plate;CPV-750/SMART-II;;;00462
1110081;馬達皮帶輪;Motor Pully;P60-8YU-35-φ48(有鍵);S45C;染黑;1110081
```

第一欄是**比對鍵，對應圖層名稱**（現場慣例是「一個零件一個圖層，圖層名 = 料號」），
比對時兩邊都 `strcase` 轉大寫。`TAG5`（#圖號）ERP 沒有對應欄位，直接複製料號。

**為何用分號而不是 TAB**：實測 TAB 在 8 萬筆資料裡零衝突，本來是最佳分隔符。
但 `get_taglist` 在 `MANAPART.lsp` 與 `campro.lsp` 各有一份、都把 `";"` 寫死，
改分隔符會牽動兩個共用函式。改由轉檔腳本保證欄位值不含分號（175 列已改全形），
分隔一樣安全，而共用函式完全不動。

**匯出格式的取捨**（實測，別再走錯路）

| 格式 | 筆數 | 中文 | 結論 |
|------|------|------|------|
| Text with headers | 83,623 行 | **874 個字元變 `?`** | 匯出時就毀了，無法還原 |
| Excel8 (97-2003) | **65,534**（截斷）| 完好 | `.xls` 有 65,536 列上限 |
| **XML** | 83,205 | **完好** | **採用** |

Text 匯出走系統 ANSI codepage（Big5），簡體字與 `Ø` `∅` 在那一刻就變成 ASCII 問號
（0x3F），不是「顯示不出來」而是資料真的沒了。XML 是 UTF-16LE，字元完好且無列數上限。

XML 有一個 XML 1.0 不允許的控制字元（料號 `1300091` 的品名開頭有 `\x1E`），
腳本會清掉；未跳脫的 `&` 有 0 個。

**字元替換**：輸出必須是 cp950（§3.1），而 XML 裡有 123 種 cp950 表示不了的字元、
影響 1,198 列。腳本把它們換成**等義字**而不是問號：

```
Ø ∅ ø ɸ → φ (1,050+)    堃 → 坤 (119)     ² → 2      ˚ ﾟ → °
簡體 → 繁體：钣→鈑、库→庫、门→門、动→動、压→壓…（約 100 字）
```

替換表在 `tools/xml2partdata.py` 的 `REPLACE`。腳本開工前會先確認每個替換目標
本身都能用 cp950 寫出來，遇到表裡沒有的字會列出來要求補上。實測結果：**0 個問號**。

**更新流程**：ERP 匯出 XML → `python tools\xml2partdata.py <來源.xml>` → 完成。
腳本會印出處理報告（替換了哪些字、修了幾列、有沒有需要人工確認的）。

### 10.6 `&cap_sybom`（PDMBOM3）：功能與收斂決策

**這支程式做什麼**（檔頭註解：「凱柏連結晶英 ERP 系統 pdmbom3」）

```

⑦ (load "pdm-cad")(c:cad_to_pdm)    ← 寫進 POWERPDM    【已移除】
```

**為何移除 ⑥⑦**（2026-09-10，使用者決定）

- 晶英 ERP 的資料庫已停用（同 campro，見 §10.5）
- PDM 模組於移植時刻意移除（§6 已完成第 3 項）。`pdm-cad.lsp` 只剩
  `PDMSERVER\Autocad\` 底下的殘留，不在支援路徑上，`(load "pdm-cad")` 必定失敗。

  在 `config.doc` 裡根本沒有設定，一樣會炸。

**資料檔本身的產生一直是正確的**，錯誤只發生在這兩個外送步驟。現在改為印出
檔案路徑，由使用者自行取用。這與把 `bomtree` 收斂成只輸出 `.csv`（§10.8）

### 10.8 物料清單匯出：現況與 `.xlsx` 優化方案（未做）

**現況**（2026-09-10 修復並實測通過）

`&bomtree1`（選單「物料清單匯出到Excel」）→ `COMMAND.lsp:396` → `(bomtree 1)`
→ `MANAPART.lsp` 的 `bomtree`。

修了兩處：

1. `(open "c:\\bompath.txt" "w")` 失敗導致整個功能無聲死亡（§5.11）。
   對 `&bomtree1`（typ=1）而言加守衛跳過即可，因為它不啟動任何外部程式。

   > **2026-09-11 更正**：當時我在程式註解與此處都寫了「`bompath.txt` 只是
   > 寫給 `manadwg.exe` 認路徑的，所以寫不成功無所謂」——**對其他 typ 而言是錯的**。
   > 使用者實測 `&bomtree0` 時 `bom1.exe` 直接跳出
   > `Cannot open file c:\bompath.txt.`。`bom1.exe` 與 `tree1.exe` 都要靠
   > 這個檔才知道 `POWDESIGN_path` 在哪，因為那兩支 exe 的年代路徑寫死在
   > `C:\DESIGNER6`。判斷錯誤的原因：只查了「哪些 LISP 程式碼讀它」，
   > 而那兩支是二進位檔查不到，卻仍下了肯定的結論（§9.5）。
2. 原本存成 `.xls`，但內容是分號分隔的純文字，Excel 開啟時全部擠在 A 欄，
   還會跳「格式與副檔名不符」。改存 `.csv` 並在第一行寫 `sep=;`。

`sep=;` 是必要的——Excel 的 `.csv` 依「系統清單分隔符」分欄，繁中 Windows
預設是逗號而非分號。資料本身維持分號分隔沒動，因為改成逗號會撞到欄位內容裡的逗號。

輸出格式（12 欄，欄名來自 `title.txt`）：

```
sep=;
層名;品名;材質;#圖號;製圖;數量;表面處理;英文品名;規格;機種;備註;廠牌
500800025;啟動貼紙;0.5t PVC貼紙;500800025;;;;ON MARK;;;;
```

> **已知小瑕疵**：`(open (strcat fname ".csv") "w")` 用的是**相對路徑**，
> 檔案會落在 DraftSight 當下的工作目錄。使用者輸入完整路徑（`C:\temp\test`）
> 可以指定位置，但預設行為不直覺。要修的話，可考慮預設寫到 `powdesign_path`
> 或跳出檔案對話框（`getfiled`）。

**`.xlsx` 優化方案（未做）**

使用者希望輸出真正的 Excel 2019 格式。**AutoLISP 做不到**——`.xlsx` 是 ZIP 壓縮檔
（內含 XML），AutoLISP 沒有壓縮能力。三條可行路線：

| 方案 | 做法 | 代價 |
|------|------|------|
| **A**（已採用）| `.csv` + `sep=;` | 無。但不是真正的 xlsx，沒有欄寬／格式／數字型別 |
| **B** | 改寫成 SpreadsheetML（`.xml`）| 純文字，AutoLISP 寫得出來。Excel 開得起來且有真正的欄位結構，可設欄寬與粗體標題。要把每一列包成 XML 標籤並跳脫 `& < > "`，改動中等 |
| **C** | LISP 寫文字檔 → `startapp` 外部轉檔程式 → 真 `.xlsx` | 真正的 xlsx。多一個要維護的元件，需要 Python 環境或包成 exe |

**方案 C 的實作建議**：架構上是順的，因為 `bomtree` 本來就有 `startapp` 的先例
（`tree1.exe` / `bom1.exe`）。可沿用 `tools/xml2partdata.py` 已驗證的模式：

```
bomtree 寫出 <fname>.csv
   → (startapp (strcat powdesign_path "tools\\csv2xlsx.exe") fname)
   → 產生 <fname>.xlsx，可順便設欄寬、凍結標題列、把數量欄轉成數字型別
```

Python 端用 `openpyxl` 幾十行就能完成（**注意本機目前沒裝 openpyxl**，
`tools/xml2partdata.py` 是刻意只用標準函式庫寫的）。若要避免 Python 相依，
可用 PyInstaller 包成單一 exe 放進 `tools/`。

**判斷標準**：如果這份清單只是開來看、再自行另存成 Excel，方案 A 就夠了；
如果要當成交付給客戶或上游系統的檔案（需要格式、需要數字欄位真的是數字），
才值得做 C。**使用者 2026-09-10 表示 A 目前夠用，C 列為日後優化。**

### 10.9 v3 → v4 的更正（2026-09-10）

v4 修正了 v3 的四處錯誤。列在這裡是因為每一處都曾造成錯誤的優先序判斷：

| 位置 | v3 的說法 | 實際 |
|------|----------|------|
| §7.1 | `autoSHSCAL` 屬性寫入是「最高優先、擋住主線」，權宜寫法用 `attdia 1` | 早在 75f9e4e 就改用 `attreq 0` 解決了。手冊的程式碼片段沒跟原始檔同步 |
| §3.2 | 10 支 Big5 檔「不在載入鏈上，優先度低」 | `HP-K.LSP`（出圖 ×3，在選單上）與 `PDMBOM3.LSP` 都在延遲載入鏈上。兩支均已於 2026-09-14 轉為 UTF-8 |
| §7.2 | `HP-K.LSP` 括號 −1 | 誤判——`;\|…\|;` 區塊註解造成，該檔實際平衡 |
| §5.3 | `attdia 0` 無效 → 暗示同類變數也無效 | `attreq 0` **有效**（§5.7）|

**共同根因**：v3 是照「檔案清單 + 分類」建立現況的，沒有跟著**呼叫關係**走，
程式碼片段也是手打進手冊、沒跟原始檔綁定。

**因此 v4 起的規則**：手冊裡的程式碼片段與檔案清單都要標註「來源檔:行號」，
讓下一個人能一眼查核，而不是重新考古。
