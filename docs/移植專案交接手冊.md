## 0. 給接手者的三分鐘版本

- 這是把一套跑了二十多年的 AutoCAD LISP 機械設計外掛（藝祥「機械設計家」Designer6 + POWERPARTS），
  移植到 **DraftSight** 的專案。程式碼是 AutoLISP + DCL，資料是 INI/DAT/DWG/SLD。
- 兩個資料夾、兩套程式：`C:\DESIGNER6_DS`（主系統）與 `C:\POWPARTS_DS`（零件庫）。
  對照組原版留在 `C:\DESIGNER6` 與 `C:\POWPARTS`，**不要動它們**——那是唯一的比對基準。
  唯一的例外是 `SHEET/A1~A4.dwg` 與 `A1~A4tzt.dwg`，這 8 個檔已在 DraftSight 重存過，
  不再與原版一致（§7.1）。
- 移植的主體工作（去加密狗、去 PDM、編碼轉換、載入鏈、選單）**已經做完**，
  現在是逐一功能實測與修 bug 的階段。
- 這個專案**沒有自動化測試**。所有驗證都得由使用者在 DraftSight 裡實際跑指令。
- 最容易踩的三個雷：**檔案編碼**、**換行符與 git**、**DraftSight 與 AutoCAD 的 LISP 行為差異**。
  三者都在下面有專章。

## 2. 環境與啟動

### 2.1 DraftSight 設定

- **Support Files Search Path** 需包含 `C:\DESIGNER6_DS` 與 `C:\POWPARTS_DS`
- **選單載入**：`CUSTOMIZE` → 載入 `C:\DESIGNER6_DS\Powsoft_Light.xml`

- **自動載入**：DraftSight 啟動時執行內建 `start.lsp`，帶起 `startup.lsp`

### 2.2 啟動鏈

```
DraftSight 啟動
  → start.lsp（DraftSight 內建）
    → startup.lsp（C:\DESIGNER6_DS，11 行）
      → (load "command")   → COMMAND.lsp（832 行，所有 c: 指令的進入點）
      → (load "quickey")   → QUICKEY.lsp
      → (c:autoload)
          → (load "designer") → designer.lsp（5 行，只是轉接）
              → (load "PUB-LISP")
              → (load "config") → config.lsp（167 行）
                  → 讀 config.doc（英文 key、cp950）
                  → 設定 POWDESIGN_path、POWERPARTS_PATH 等全域路徑變數
          → (loaddesigner) → SYSTEM.lsp
              → get_layerdef / get_ltypedef / get_bomdef / get_bomlistdef
                 ← 目前一律回傳程式內建預設值（繞過 system.ini 讀取問題）
          → 若存在 campro.lsp 則載入（ERP 連結模組，選配）
```

> **已知小瑕疵**：`startup.lsp` 裡 `(load "command")` / `(load "quickey")` / `(c:autoload)`
> 各出現兩次（重複貼上）。目前不影響運作（`c:autoload` 內有 `POWDESIGN_path` 是否已設的守衛），
> 但會讓啟動多跑一次載入。整理時可一併移除。

## 3. 編碼規範（最重要的一章）

### 3.1 規則

| 類型 | 必須編碼 | 理由 |
|------|---------|------|
| `.lsp` | **UTF-8**（無 BOM） | DraftSight 2025 可正確讀取 |
| `.dcl` | **cp950 / Big5** | DraftSight 不支援 UTF-8 DCL，`load_dialog` 回傳 -1 |
| `.ini` `.doc` `.dat` `.txt` | **cp950 / Big5** | DraftSight 的 `open`/`read-line` 以 cp950 讀檔，UTF-8 會亂碼 |
| `.md` `.gitignore` `CLAUDE.md` | UTF-8 | 給人和工具讀 |

**同一個檔案內絕不可混用編碼。**

### 3.2 實測現況（2026-09-09）

DESIGNER6_DS，77 支 `.lsp`：

| 分類 | 數量 | 說明 |
|------|------|------|
| 純 UTF-8 | 64 | 正常 |
| 純 ASCII | 3 | 無中文，無所謂 |
| 純 Big5 | 10 | **尚未轉換**，見下表 |
| 混編碼 | 0 | 曾有 1 支，已於 c690ade 修正 |

尚未轉 UTF-8 的 10 支。**注意：其中 2 支在載入鏈上，不是「全部都是舊版備份」**（v3 的敘述有誤，2026-09-10 更正）：

| 檔案 | 是否在載入鏈上 | 優先度 |
|------|--------------|--------|
| `HP-K.LSP` | **是** — `COMMAND.lsp:123-126` 的 `c:&hp` / `&hp2` / `&hp3` / `&batch_plot` 延遲載入 | **高**，見 §7.3 |
| `PDMBOM3.LSP` | **是** — `COMMAND.lsp:121` 的 `c:&cap_sybom` | 低，該指令不在選單上 |
| 其餘 8 支 | 否 | 低 |

判斷「在不在載入鏈上」不能只看 `startup.lsp`——`COMMAND.lsp` 是**延遲載入**架構
（`(cond ((null c:hp)(load "hp-k"))(t (princ)))`），要掃那 832 行裡的每一個 `(load ...)`。

完整的 10 支清單：

```
COMMAND-.LSP        HP-K-old.LSP        HP-K.LSP
KB/COMMAND.LSP      KB/LOADSYS.LSP      KB/SETUP.LSP
PDMBOM3.LSP
PDMSERVER/Autocad/ACADDOC.OLD.LSP
PDMSERVER/Autocad/PUB-LISP.LSP
PDMSERVER/Autocad/WORDLIB1.LSP
```

POWPARTS_DS，114 支 `.lsp`：純 UTF-8 84 支、純 ASCII 30 支、**沒有殘留 Big5、沒有混編碼**。

`.dcl` 36 支全為 cp950（1 支純 ASCII）；`.ini` 8 支 cp950 / 6 支 ASCII。符合規範。

### 3.3 ⚠ 已造成的永久損傷：U+FFFD

早期一次 Big5→UTF-8 批次轉換使用了 `errors='replace'`，無法解碼的位元組被換成 U+FFFD（`�`）。
這些中文**已無法從 _DS 版本還原**：

| 檔案 | U+FFFD 個數 |
|------|------------|
| `MANABLK.lsp` | 4,712 |
| `COMMAND.lsp` | 3,295 |
| `SCRWLINE.lsp` | 2,103 |
| `TRAP_DIR.lsp` | 1,295 |
| `AUXEDIT2.lsp` | 529 |
| `ermsg.lsp` | 19 |
| **合計** | **11,953** |

POWPARTS_DS 完全沒有這個問題（0 個）。

**還原可行性（實測）**：這 6 支在 `C:\DESIGNER6` 都有原檔，但其中 5 支**原檔本身就不是合法的 cp950**
（只有 `COMMAND.lsp` 的原檔可以乾淨解碼為 cp950）。也就是說原始碼裡本來就混有非 Big5 的位元組，
不是單純換個轉換參數就能救。要修復需要逐檔人工比對，並非批次作業。

> **規則：不要再對 `.lsp` 跑批次編碼轉換。** 再跑一次只會製造更多 U+FFFD。
> 個別檔案需要修時，逐檔處理並在轉換時用 `errors='strict'`，失敗就停下來人工看。

### 3.4 動手前的檢查指令

```bash
# 驗 UTF-8
python3 -c "open('SHSCAL.lsp','rb').read().decode('utf-8'); print('UTF-8 OK')"
# 驗 cp950
python3 -c "open('shscal.ini','rb').read().decode('cp950'); print('cp950 OK')"
# 找出檔案裡非 UTF-8 的行號（用來抓混編碼）
python3 - <<'PY'
bad=[]
for i,l in enumerate(open('SHSCAL.lsp','rb').read().split(b'\n'),1):
    try: l.decode('utf-8')
    except UnicodeDecodeError: bad.append(i)
print('非 UTF-8 行:', bad or '無')
PY
```

## 4. 換行符與 git

repo 歷史是以 `core.autocrlf=true` 從 Windows 提交的：**版本庫存 LF、工作目錄存 CRLF**。

若在沒有這個設定的環境（例如 Linux、或透過網路磁碟掛載）操作 git，
`git status` 會把 **265 個檔案全部誤判為已修改**——那不是真的改動，是換行符解讀差異。

```bash
git config --get core.autocrlf    # 必須是 true
git config core.autocrlf true     # 不是就設定它（已於 2026-08-28 設好）
```

**症狀辨識**：`git status` 一次冒出上百個沒印象改過的檔案 → 先查這一項，不要照單全收去 commit。
一旦把 CRLF 提交進版本庫，之後所有人的 diff 都會爛掉。

### git 鎖檔陷阱

透過網路磁碟或受限掛載操作 git 時，`.git/index.lock`、`.git/HEAD.lock`、`.git/objects/tmp_obj_*`
可能因為無刪除權限而殘留，卡住後續所有 git 指令（`fatal: Unable to create index.lock: File exists`）。

```bash
rm -f .git/index.lock .git/HEAD.lock .git/objects/maintenance.lock
find .git/objects -name "tmp_obj_*" -delete
```

## 5. DraftSight 與 AutoCAD 的 LISP 行為差異

這是移植過程中最花時間的部分。以下每一條都是實際踩過的坑。

### 5.1 `load_dialog` 需要副檔名

AutoCAD 的 `(load_dialog "shscal")` 會自動補 `.dcl`，DraftSight 不會，會回傳 -1。

**修法**：`PUB-LISP.lsp` 的 `actdcl` 一律補副檔名 → `(load_dialog (strcat filename ".dcl"))`。已修。

### 5.2 `read-line` 不吐檔尾空行 ［推論，未實機查核］

**症狀**：`shscal.ini` 最後一段（`**凱柏圖框`）的最後一筆 `ASMA3` 在圖紙尺寸清單裡消失，
但非最後一段（`**凱柏零件圖框`）的 `A4` 正常。

**成因**：`SHSCAL.lsp` 的 `read_autoshscal_data` 原本把每段讀到的列一路 `cons` 進 `rdlist`，
再用 `(reverse (cdr rdlist))` 取出——那個 `cdr` 是**刻意**用來丟掉「段尾空白行」產生的 nil。
整個解析因此相依於「每段後面都有一行空白行」。檔案最後一段的空白行位在 EOF 前，
AutoCAD 的 `read-line` 會先回 `""` 再回 `nil`，DraftSight 推測是直接回 `nil`，
`rdlist` 的頭就變成最後一筆資料而被 `cdr` 丟掉。

**修法**（commit 52f6a64）：改成只收集以 `(` 開頭的有效資料列，直接用 `(cons nn (reverse rdlist))` 組裝，
不再依賴空白行、也不再用 `cdr` 丟東西。這個修法不管 `read-line` 的實際行為如何都正確。

**驗證推論的方法**（尚未執行）：在 DraftSight 命令列跑

```lisp
(setq f (open "C:\\DESIGNER6_DS\\shscal.ini" "r") n 0)(while (read-line f)(setq n (1+ n)))(close f)(princ n)
```

AutoCAD 應為 33。DraftSight 若回 32，即證實 `read-line` 不吐檔尾空行。

> **通用教訓**：原始碼裡任何「靠空白行、檔尾格式、行數當 sentinel」的寫法，在移植版都是高風險。
> 看到 `(cdr rdlist)`、`(reverse (cdr ...))` 這類寫法要優先懷疑。

### 5.3 `attdia 0` 無效

AutoCAD 的 `attdia 0` 讓 `INSERT` 改在命令列詢問屬性，可以用 `repeat n (command "")` 跳過。
DraftSight 的 `attdia 0` **完全無效**，插入含屬性的 block 時強制彈出對話框。

**影響**：曾擋住 `auto_insert_attsheet` 插入 `*tzt.dwg` 的流程。
**已解決**——改用 `attreq 0` 繞過，見 §5.6。

### 5.4 `entnext` / `entget` 限制

在某些情況（特別是 `command` 執行後），`entlast` 取得的 entity name 可能失效。
必須在 `command` **執行完成後立即**取得，不能跨函式傳遞。

### 5.5 動態作用域行為不同

`input_attedata` 從 `ATOshscal` 呼叫時，讀不到 `ATOshscal` 的區域變數（`?scl`、`sfilename` 等）。

**修法**：呼叫前把需要的值存成全域（命名慣例 `&&vctr`、`&&scl`、`&&sfilename`…），
並把 `attdata_list` 從 `ATOshscal` 的區域變數列表移除讓它變全域。已修。

### 5.6 `attreq 0` **有效**（與 `attdia 0` 相反）

`attdia 0` 在 DraftSight 完全無效（§5.3），但 **`attreq 0` 有效**，2026-09-10 實機證實。

`attreq 0` 讓 `INSERT` 用 block 定義的預設值靜默填入屬性，**既不彈對話框也不在命令列詢問**。
這正是移植 `auto_insert_attsheet` 的關鍵——原版靠 `attdia 0` +
`(repeat attqty (command ""))`（按 27 次 Enter 吃掉命令列提示）達到同樣效果，
移植版改用 `attreq 0` 之後那個 `repeat` 就不需要了。

**實測方法**（可重複驗證，開一張新圖再跑）：

```lisp
(setvar "attdia" 0)(setvar "attreq" 0)(command "insert" "C:\\DESIGNER6_DS\\SHEET\\A4tzt" '(0 0 0) 1 1 0)(princ (strcat "\ncmdactive=" (itoa (getvar "cmdactive"))))
```

實測結果：圖框直接插入、無對話框、無屬性提示、`cmdactive=0`。
插入後的 block 有 27 個 ATTRIB、group 66 旗標為「有」，屬性實體確實建立了，
所以後續 `chg_sheetatt` 有東西可以覆寫。

> **附帶證實**：命令視窗的回顯顯示 `insert` 的 5 個參數（名稱、插入點、X 比例、Y 比例、角度）
> 逐一對上，沒有錯位。原版給 Y 比例傳空字串 `""`，移植版改成明確傳 `?scl` 是對的。

**通用教訓**：不要因為 `attdia` 被忽略就假設同類系統變數也被忽略。
DraftSight 對 AutoCAD 系統變數的支援是逐一不同的，每個都要單獨實測。
測法是三段式——① `(getvar "x")` 變數存不存在 ② `(setvar "x" v)` 設不設得進去
③ **實際跑一次相關指令**看有沒有生效。①② 過了 ③ 不一定過，`attdia` 就是這樣。

### 5.7 中文 key 讀取問題

`system.ini` / `shscal.ini` 原本用中文當 key（`圖層定義`、`圖框日期型式`…），DraftSight 下讀取有問題。
已全面改為英文 key，並同步更新 17 支讀取這些 ini 的 LSP。對照表見 §10。

## 7. 已知問題

### 7.1 ✅ `autoSHSCAL` 屬性寫入（已解決，2026-09-10）

> v3 把這條列為「最高優先、擋住主線」，**但那是誤判**：v3 的程式碼片段是手打進手冊的，
> 沒跟原始檔同步，而修法早在 commit 75f9e4e 就進去了。教訓見文末。

**最終寫法**（[`SHSCAL.lsp`](../SHSCAL.lsp) 的 `auto_insert_attsheet`）

```lisp
(command "insert" sfilename vctr ?scl ?scl "0")                 ; 插入外框（無屬性）
(setvar "attreq" 0)                                             ; ← 關鍵：靜默填入預設值
(command "insert" (strcat sfilename "tzt") vctr ?scl ?scl "0")
(setq tzt_ent (entlast))                                        ; 必須立即取得（§5.4）
(setvar "attreq" 1)
;; ... MOVE 圖框 ...
(if attdata_list (chg_sheetatt tzt_ent attdata_list))           ; 用對話框的值覆寫
```

與原版的差異：

| | 原版（AutoCAD） | 移植版 |
|---|---|---|
| 吃掉屬性提示 | `(repeat attqty (command ""))` 按 27 次 Enter | `attreq 0`，不需要 |
| Y 比例 | `""`（接受預設） | 明確傳 `?scl` |
| 覆寫條件 | `(if (= "1" instype) ...)` | `(if attdata_list ...)` |
| 找不到 tag | 無檢查 → `(entmod nil)` | `(if data1 ... (princ "[WARN] ..."))` |

`attqty` 因此變成**死變數**（還被設定但沒有消費點）。這是好事：
原版依賴「ini 裡手工維護的數字」要跟「DWG 實際屬性數」一致，移植版不再有這個相依性。

**IDX 的根因**（實測通過前的最後一個障礙）

實測時出現 `[WARN] chg_sheetatt: tag not found: IDX`。查核結果：

| 來源 | 數字 |
|------|------|
| `shscal.ini` A1~A4 屬性定義 | 27 |
| `shscal.ini` 宣告的 `attqty` | 27 |
| `A4tzt.dwg` 當時實際 ATTDEF | **26**（缺 IDX）|

`shscal.ini` 一直是對的，**是 DWG 漂移了**——IDX 屬性定義在某次編輯中從圖框檔裡消失。
這一個根源同時造成兩個症狀：`chg_sheetatt` 找不到 tag，以及原版 `(repeat 27 ...)`
會對 26 個提示多按一次 Enter。

`C:\DESIGNER6` 原版的 `shscal.ini`（27 筆、`attqty=27`）與 `A4tzt.dwg`（26 個）**同樣不一致**，
所以這是原版就存在的資料漂移，不是移植造成的。原版沒出事的原因推測是
`(= "1" instype)` 這個較窄的條件讓 `chg_sheetatt` 很少被走到。

**修法**：在 DraftSight 裡為 `SHEET/A1~A4tzt.dwg` 各補一個 `IDX` 屬性定義
（標籤 `IDX`、提示「設變順次」、預設值空白），做法是複製既有的 `CHANGENO` 屬性定義再改標籤，
這樣文字樣式／字高／圖層／顏色自動繼承。補完後三方數字全部對齊為 27，
標籤集合與 ini 定義**完全一致、零差異**。`ASMA1~3tzt.dwg` 不需要改（ini 定義本來就沒有 IDX）。

> ⚠ **`SHEET/A1~A4.dwg` 與 `A1~A4tzt.dwg` 已不再與 `C:\DESIGNER6` 原版一致。**
> 這 8 個檔在 DraftSight 2025 裡重存過（外框檔其實不需要改，是連帶被重寫），
> 檔案大小普遍縮小 12~34 KB（不同格式／壓縮／清掉未使用定義）。
> 使用者實測插入正常。**之後這 8 個檔不能再用 diff 原版來排查。**

**驗證屬性清單的指令**（在 DraftSight 開啟該 DWG 後貼到命令視窗）

```lisp
(setq e (entnext) n 0)(while e (if (= "ATTDEF" (cdr (assoc 0 (entget e)))) (progn (setq n (1+ n))(princ (strcat "\n" (cdr (assoc 2 (entget e))))))) (setq e (entnext e)))(princ (strcat "\n=== ATTDEF 總數=" (itoa n)))
```

下一個人會照著錯誤的現況排優先序。§7.x 與 §3.2 都因此誤導過。

### 7.2 括號不平衡的檔案

位元組層級掃描偵測到以下 `.lsp` 括號不平衡（`depth` 為正表示多了左括號）：

| 檔案 | depth | 備註 |
|------|-------|------|
| `TRAP_DIR.lsp` | +10 | 同時含 1,295 個 U+FFFD |
| `SCRWLINE.lsp` | +6 | 同時含 2,103 個 U+FFFD |

| `FIELDSET.lsp` | −1 | |
| ~~`HP-K.LSP`~~ | ~~−1~~ | **誤判，已排除**（見下）|

**注意**：Big5 檔的第二位元組可能剛好是 `(` `)` `"` `\`，所以位元組層級的括號掃描
**只對 UTF-8 檔有效**，對 Big5 檔的結果不能採信。上表都是 UTF-8 檔。

前四支的不平衡很可能就是 U+FFFD 損毀造成的——原本被吃掉的位元組裡含有括號。
修復這些檔案等同於修復 §3.3 的損傷，需人工逐檔比對原版。

**`HP-K.LSP` 的 −1 是誤判**（2026-09-10 更正）。兩項查核：

1. 第 160–198 行是 `;|` … `|;` **區塊註解**（一份被註解掉的舊 `batch_plot`），
   真正的 `c:batch_plot` 定義在第 200 行。掃描器不認得區塊註解才數出 −1。
2. 掃過該檔所有 Big5 雙位元組字元的尾位元組，落在 `(` `)` `"` `\` 上的有 **0 個**，
   所以「Big5 掃描不可靠」的警告對這支不適用。

按 cp950 正確解碼後 `HP-K.LSP` 與 `PDMBOM3.LSP` **都平衡到 0**，字串全部閉合。
寫掃描工具時記得處理 `;|…|;`，否則會製造假警報。

### 7.3 `HP-K.LSP`：出圖功能尚未移植（高優先）

`HP-K.LSP` 撐著三個**選單上的**功能——印表機出圖（1.1.10）、繪圖機出圖（1.1.11）、
批次出圖（1.1.12）。它與 `C:\DESIGNER6\HP-K.LSP` **位元組完全相同**（12,560 bytes），
從頭到尾沒被移植過。狀態是「**未移植**」而不是「未測」——測了一定失敗，而且不只一個原因：

**問題一：中文是功能參數，不是提示訊息**

```lisp
;; HP-K.LSP:74-80、120-125
(hp2_plot "較大尺寸：ISO A1  (portrait)" "A1")
;; → HP-K.LSP:93
(command ".plot" "Y" "MODEL" "HP DesignJet 500 42 by HP(POWER)" paper_size "M" "L" ...)
```

那個中文字串是**餵給 PLOT 指令的紙張尺寸名稱**，必須跟印表機驅動回報的字串逐字相符。
檔案是 Big5、DraftSight 以 UTF-8 讀 `.lsp` → 字串亂掉 → 對不上。

**問題二：就算編碼修好也還是壞的**

那是*中文版 AutoCAD* 的紙張尺寸標籤，加上寫死的繪圖機名稱
`HP DesignJet 500 42 by HP(POWER)`，以及 AutoCAD `.plot` 的參數序列。
DraftSight 的出圖指令語法與紙張名稱都不同。

**因此**：這支要重新移植（改編碼 + 換出圖指令 + 紙張名稱改成 DraftSight 的），
不是改個編碼就能過。排工作量時要當成一次移植，不是一次測試。
另注意它在第 302 行重新定義了全域 `*error*`，載入後會影響整個 session 的錯誤處理。

### 10.4 `shscal.ini` 格式

```
DATE_FORMAT=1                    ← 原「圖框日期型式」
POWERPDM_FRAME_MAP=(...)         ← 原「POWERPDM圖框屬性與CAD圖框對應」
ALL_SHEET_SCALE_TAG="SCALE"

**凱柏零件圖框                    ← ** 開頭 = 段名，即「圖紙型式」下拉選項
("A1" "A1" "C:\\DESIGNER6_DS\\SHEET\\A1" (786 491) ((屬性定義...)) "27" "SCALE")
("A2" ...) ("A3" ...) ("A4" ...)

**凱柏圖框
("ASMA1" ...) ("ASMA2" ...) ("ASMA3" ...)
```

每列欄位依序為：圖紙名稱、圖紙尺寸、圖檔路徑、`(空白區寬 高)`、屬性定義串列、屬性總數、比例屬性標籤。

**屬性定義串列**的每一筆是 3 或 4 個元素：

```
("PARTNO" "每台件數" "每台件數")          ← 3 元素：使用者手動填
("DWGNO"  "圖號"     ""        "F")      ← 4 元素：第 4 個是自動填值碼
```

`(tag 對話框提示 對應名稱 [自動填值碼])`

**自動填值碼**由 [`SHSCAL.lsp:1232-1239`](../SHSCAL.lsp) 的 `(setq code_id (nth 3 nn))` 讀取，
在「圖框屬性」對話框開啟時自動預填該欄位：

| 碼 | 意義 | 填入來源 | 唯讀 |
|----|------|---------|------|
| `S` | 比例 | `SCALETXT` | 是（`mode_tile 1`）|
| `T` | 圖紙尺寸 | `sheetsize` | 是 |
| `D` | 日期 | `getsys_date` + `DATE_FORMAT` | 否 |
| `F` | 檔名 | `(curdwgname)` | 否 |
| `Q` | 數量 | ［未查核］A1~A4、ASMA1~3 都沒用到 | |

A1~A4 與 ASMA1~3 各有 **3 筆**帶碼定義，且七個圖框完全相同：
`DWGNO`→`F`、`DATE1`→`D`、`SCALE`→`S`。

**各圖框的定義筆數**（2026-09-10 實測，用 LISP tokenizer 解析而非 regex）：

| 圖框 | 定義筆數 | `attqty` | DWG 實際 ATTDEF |
|------|---------|----------|----------------|
| A1~A4 | 27 | 27 | 27（補回 IDX 後，§7.1）|
| ASMA1~3 | 13 | 13 | ［未查核］|

> ⚠ **解析這個檔不要用 regex。** 屬性定義的第 3 欄可能含括號（`"零件品名(C)"`），
> 筆數又可能是 3 或 4，兩種常見的 regex 寫法會各漏一邊——實際踩過，
> 先算出 24 再算出 25，正確答案是 27。要嘛寫個小的 LISP reader，
> 要嘛直接在 DraftSight 裡用 `(read ...)` 讓 LISP 自己解。

程式碼片段也是手打進手冊、沒跟原始檔綁定。

**因此 v4 起的規則**：手冊裡的程式碼片段與檔案清單都要標註「來源檔:行號」，
讓下一個人能一眼查核，而不是重新考古。
